Learning by Gradient Descent

One algorithm trains almost everything: predict, measure how wrong you were, nudge the parameters downhill, repeat. Build it once here on a straight line, and GPT-scale training is the same loop with more parameters and more plumbing.

  • Write down a model, a loss and an update rule
  • Train a real regression in the page and watch the loss fall
  • Feel what a learning rate that's too big or too small does
  • Choose between full-batch, mini-batch and stochastic updates
  • Extend the same machinery to classification with logistic regression

The smallest possible model

Predict house price from size: ŷ = w·x + b. Two parameters. w is how much price moves per square metre; b is where the line crosses zero. Training means finding the w, b that make the predictions least wrong across all the data.

“Least wrong” needs a number. For regression the default is mean squared error:

MSE = (1/n) · Σ (ŷᵢ − yᵢ)²      # average squared residual

Squaring does two useful things: it removes the sign (being 5 too high is as bad as 5 too low) and it punishes big misses far more than small ones. It also has a smooth derivative, which is what lets us do calculus on it.

Where the update rule comes from

You want the derivative of the loss with respect to each parameter. For MSE with one feature, it falls out in two lines:

# prediction and error for one example
ŷ = w·x + b
e = ŷ − y

# how the loss changes as w and b change
∂MSE/∂w = (2/n) · Σ e·x      # errors weighted by the input
∂MSE/∂b = (2/n) · Σ e        # just the mean error

# the step: move against the gradient
w ← w − η · ∂MSE/∂w
b ← b − η · ∂MSE/∂b
💡
Read the gradient, don't memorise it

Σ e·x says: if the examples where we predict too high tend to have large x, then w is too big. That's the whole intuition. Every gradient in deep learning has this flavour — “how much did this parameter contribute to the error, in the direction it was pushed?”

The learning rate is the whole game

η controls stride length. It is the hyperparameter you will tune more often than any other, and its failure modes are visually obvious once you've seen them.

🐌

Too small

Loss falls, but glacially. You'll conclude the model can't learn when actually you didn't wait. Costs you GPU-weeks at scale.

✅

Just right

Fast drop, then a smooth flattening. Usually the largest rate that doesn't spike — found with a short LR-range test (Chapter 9).

💥

Too large

The step overshoots the valley and lands higher up the opposite slope. Loss oscillates, then becomes NaN. Classic first-day-of-training failure.

📐
Unscaled features make η impossible to choose

If rooms ranges 1–6 and square_metres ranges 20–400, the loss surface is a long narrow canyon. The rate that's safe for the steep direction is far too small for the shallow one, so training zig-zags. Standardizing features (Chapter 4) turns the canyon into a bowl — the single highest-value preprocessing step for gradient-based models.

Full batch, mini-batch, or one at a time?

The gradient over the entire dataset is the “true” direction, but computing it for 400 million examples per step is absurd. In practice you estimate it from a mini-batch.

ModeGradient per stepProsCons
Full batchAll n examplesExact direction, smooth curveOne step per pass — hopeless at scale; can't fit in memory
Mini-batch (32–4M tokens)A random subsetHardware-efficient, noise helps escape bad minimaBatch size interacts with learning rate and generalization
Stochastic (n=1)One exampleUpdates immediately; useful for online learningVery noisy, terrible GPU utilization
⚖️
Batch size in one sentence

Bigger batches give a less noisy gradient, so you can use a bigger learning rate (a common rule: scale η roughly with batch size, or with its square root) — but past a point extra batch size buys accuracy per step that costs more compute than it saves. Chapter 23 shows how this drives distributed training design.

From regression to classification: logistic regression

Now predict a probability, not a number. Keep the same linear core, squash it through a sigmoid so it lands in (0, 1), and change the loss to cross-entropy:

z = w₁x₁ + w₂x₂ + b
p = σ(z) = 1 / (1 + e^(−z))          # probability of class 1
L = −[ y·log(p) + (1−y)·log(1−p) ]    # binary cross-entropy

∂L/∂w = (p − y) · x                   # astonishingly, the same shape as before

That last line is not a coincidence: for the natural pairing of sigmoid with cross-entropy (and softmax with categorical cross-entropy), the gradient simplifies to (prediction − truth) × input. It's why these pairings are standard.

Regularization: preferring simpler fits

Nothing stops the optimizer driving weights to huge values to squeeze out the last bit of training loss — which is overfitting (Chapter 7). Regularization adds a penalty for complexity to the objective itself.

L2 (ridge / weight decay)

Add λ·Σw². Shrinks all weights smoothly toward zero; the default for neural networks, where it is usually implemented as weight decay in the optimizer.

L1 (lasso)

Add λ·Σ|w|. Drives some weights exactly to zero, so it performs feature selection. Useful when you want a sparse, explainable model.

🎒
Analogy: packing for a trip

The loss says “bring whatever makes the trip perfect”. Regularization says “every item costs weight”. L2 makes you pack lighter versions of everything; L1 makes you leave some items behind entirely. Both stop you from carrying a wardrobe to cover every hypothetical — which is exactly what an overfitted model does.

🔬
The single best debugging trick in ML

Overfit a tiny subset first. Take 16 examples and train until the loss is ~0. If a model cannot memorise 16 examples, no amount of data or tuning will save it — you have a bug in the data pipeline, the loss or the label alignment. This takes two minutes and saves days.

⚠️
Common mistakes
  • Tuning the learning rate before scaling the features. You're tuning around a problem you could have removed.
  • Using MSE for classification. It gives tiny gradients when the model is confidently wrong — precisely when you need a big correction. Use cross-entropy.
  • Forgetting to zero gradients between steps in frameworks that accumulate them — the update ends up using a sum of every batch so far.
  • Judging a run by training loss alone. The only number that matters is on data the model has not seen.
  • Assuming convergence means correctness. Gradient descent happily converges to a great fit of a leaked feature.
🎤
Interview drill

Warm-up: Your loss goes to NaN in the first 100 steps. Walk me through the diagnosis.

How a strong answer sounds
First reproduce with a fixed seed and log the loss every step to see whether it explodes or jumps instantly. Instant NaN usually means bad input data (NaNs or infinities in features, a divide-by-zero in normalization, log of zero); a gradual explosion means the learning rate is too high or gradients are unclipped. So: check the batch's input statistics, lower the learning rate by 10×, add gradient clipping, confirm the loss function is numerically stable (use logits-based cross-entropy rather than log of a softmax output), and add a warmup. If it survives at a tiny rate, it's a rate/stability problem; if it NaNs even then, it's data.

Deeper: Why does mini-batch noise sometimes improve final quality rather than just being a compute compromise?

How a strong answer sounds
The noisy gradient acts as an implicit regularizer: it discourages settling into sharp, narrow minima that fit the training batch precisely but generalize poorly, and it lets the trajectory escape flat saddle regions. Empirically, very large batches with an unchanged schedule often generalize slightly worse, which is why large-batch training pairs bigger batches with learning-rate scaling, warmup and sometimes extra regularization. It's a trade — noise helps generalization, but too much of it wastes steps.

🧠 Key takeaways

  • Training = model + loss + optimizer; the loop is predict → measure → step downhill → repeat.
  • The gradient answers “how much did this parameter contribute to the error?”; the learning rate is the stride.
  • Standardize features before tuning the learning rate — it reshapes the loss surface.
  • Mini-batches trade gradient accuracy for hardware efficiency, and the noise mildly helps generalization.
  • Logistic regression is the same machinery with a sigmoid and cross-entropy; the gradient is still (prediction − truth) × input.

Check your understanding

Your training loss oscillates wildly and occasionally jumps upward. What's the most likely single cause?

Steps overshoot the minimum and land on the far slope. Halve the rate (or add warmup and decay) and it usually settles immediately.

Why is cross-entropy preferred over MSE for classification?

With MSE and a sigmoid, a confidently wrong prediction sits in the saturated region where the gradient nearly vanishes — so the model learns slowest when it is most wrong. Cross-entropy fixes that.

Feature A ranges 0–1 and feature B ranges 0–100,000, and you train a linear model with a single learning rate. What happens?

The loss surface becomes a narrow canyon: any rate safe for the steep direction is far too small for the shallow one. Standardize first.

You use L1 instead of L2 regularization. What is the most distinctive effect?

L1's constant-magnitude gradient pushes small weights all the way to zero, producing a sparse model — effectively automatic feature selection.

A new model's loss is completely flat from step 1. What should you try first?

If the model can't drive the loss to near zero on 16 examples, the problem is a bug — labels misaligned, gradients not flowing, a frozen layer, a zero learning rate — not a lack of data or time.

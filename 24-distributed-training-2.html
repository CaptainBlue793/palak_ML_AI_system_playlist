Distributed Training II: Tensor, Pipeline & MoE

When a single layer no longer fits, or the network can't carry the gradients, you stop splitting the batch and start splitting the model. Tensor parallelism cuts each matrix; pipeline parallelism cuts the stack; mixture-of-experts cuts the computation. Real runs use all of them at once.

Tensor parallelism: split the matrices

A linear layer Y = XW can be split by columns of W (each GPU produces some output features) or by rows (each GPU produces a partial sum). Transformers alternate the two so that one collective per sub-layer is enough.

# MLP block, 2-way tensor parallel
W1 split by COLUMNS → each GPU computes part of the hidden activations
                      (no communication: outputs are independent features)
GELU applied locally
W2 split by ROWS    → each GPU computes a partial output sum
all-reduce          → add the partials to get the true output   ← the one collective

# attention: heads are split across GPUs, then one all-reduce after the output projection
🔗
Tensor parallelism is an intra-node technique

It requires an all-reduce twice per transformer block — dozens of times per forward pass, on the critical path with nothing to overlap. On NVLink at ~400 GB/s that's tolerable; over a 25 GB/s network it destroys throughput. The near-universal rule: TP degree ≤ GPUs per node (usually 2, 4 or 8).

Pipeline parallelism: split the layers

Put layers 1–8 on GPU 0, 9–16 on GPU 1, and so on. Activations flow forward between stages, gradients flow back. The problem is obvious: while stage 0 works, stages 1–3 have nothing to do. That idle time is the bubble, and micro-batching is how you shrink it.

The bubble formula

bubble fraction = (stages − 1) / (micro_batches + stages − 1). With 4 stages and 4 micro-batches you waste 43%; with 4 stages and 32 micro-batches, 8.6%. The rule of thumb is micro-batches ≥ 4× stages. The catch is that more in-flight micro-batches means more stored activations — which is exactly what 1F1B scheduling addresses, by starting backward passes as early as possible.

Sequence and context parallelism

For very long contexts the activations for a single sequence stop fitting. Sequence parallelism splits along the token dimension: each GPU holds part of the sequence, and attention is computed by passing key/value blocks around a ring (“ring attention”), so no device ever materialises the full T×T score matrix. It composes with tensor parallelism and is how 100k+ token training runs are done.

3D parallelism: composing the dimensions

Real frontier runs combine all of them. The art is mapping each dimension onto the hardware so the chattiest one stays on the fastest link.

Mixture of Experts: more parameters, same compute

Replace the MLP in some blocks with N expert MLPs plus a router that sends each token to the top-k experts (usually k = 1 or 2). Total parameters grow N×, but each token only activates k of them — so capacity grows while FLOPs per token stay roughly flat.

Routers collapse without help

Left alone, a router discovers that sending everything to two good experts lowers loss fastest, and the rest never train. Every MoE implementation adds an auxiliary load-balancing loss that penalises uneven expert assignment, plus a capacity factor that caps tokens per expert (the excess is dropped or passed through). Watch per-expert token counts during training the way you watch the loss curve — collapse is the characteristic MoE failure.

⚠️
Common mistakes
  • Tensor parallelism across nodes. Two all-reduces per block over the network will halve your throughput or worse.
  • Too few micro-batches for the pipeline depth. A 50% bubble is a 50% waste, and the fix is a scheduling parameter, not hardware.
  • Ignoring the last pipeline stage's extra memory. Stages are rarely balanced; the first and last hold embeddings and the loss head.
  • Not monitoring MoE expert utilization. Collapse is silent in the loss curve and obvious in the routing histogram.
  • Assuming MoE is cheap to serve. Training FLOPs fall; serving memory does not.
  • Changing parallel layout without re-checking the global batch. The batch and learning-rate schedule are coupled to the DP degree.

Interview drill

Warm-up: Why is tensor parallelism kept within a node while pipeline parallelism crosses nodes?

How a strong answer sounds
Their communication profiles are opposite. Tensor parallelism needs an all-reduce of the full activation tensor twice per transformer block — frequent, latency-sensitive, on the critical path, with nothing to overlap it with. Pipeline parallelism sends only the boundary activations between adjacent stages, a handful of point-to-point transfers per micro-batch, which tolerates higher latency and lower bandwidth. So you put TP on NVLink inside a node and let PP take the slow inter-node hops, with data parallelism outermost because its one all-reduce per step can overlap with the backward pass.

Deeper: You're given 512 GPUs for a 200B-parameter model. Sketch the layout.

How a strong answer sounds
Start from memory: 200B in mixed precision with optimizer state is ~3.2 TB, so we need model sharding regardless. I'd use TP=8 within each node (NVLink), PP across nodes sized so each stage's layers plus activations fit — say PP=8, giving a model-parallel group of 64 GPUs — and DP=8 over the remaining dimension, with FSDP or ZeRO-1 inside the data-parallel groups to shard optimizer state. Micro-batches at least 32 to keep the pipeline bubble near 10%, activation checkpointing on, and sequence parallelism if the context is long. Then I'd validate rather than trust the plan: measure MFU, check the per-stage balance (the first and last stages carry embeddings and the loss head), and confirm the global batch and learning-rate schedule still match what the scaling-law work assumed.

🧠 Key takeaways

  • Tensor parallelism splits matrices and all-reduces twice per block — keep it inside a node.
  • Pipeline parallelism splits layers; the bubble is (stages−1)/(micro-batches+stages−1), so use many micro-batches and 1F1B.
  • Sequence parallelism splits the token dimension for very long contexts.
  • 3D parallelism maps the chattiest dimension to the fastest link: TP inside nodes, PP across, DP outermost.
  • MoE buys parameters without FLOPs, at the cost of all-to-all traffic, routing instability and serving memory.

Check your understanding

With 8 pipeline stages and 8 micro-batches, what fraction of time is bubble?

(8−1)/(8+8−1) = 7/15 ≈ 47%. You need roughly 4× more micro-batches than stages before the bubble becomes small.

Why is tensor parallelism across a slow network so damaging?

Dozens of blocking collectives per forward pass, with no compute to hide them behind. Data parallelism's single overlappable all-reduce per step is far more tolerant of slow links.

An MoE model has 8 experts with top-2 routing. Roughly how do parameters and per-token compute compare with a dense model of the same expert size?

All experts exist in memory; only k run per token. That's the trade: capacity scales with N, FLOPs with k — and serving memory with N, which is the part people forget.

Your MoE run shows two experts receiving 70% of all tokens. What's the fix?

Router collapse. The auxiliary loss penalises uneven assignment; capacity limits cap any single expert's share. Monitor per-expert token counts as a first-class metric.

Which parallelism dimension is best placed outermost, across the whole cluster?

Its single gradient all-reduce per step can overlap with the backward pass, so it tolerates the slowest links — which is exactly what the outermost dimension gets.

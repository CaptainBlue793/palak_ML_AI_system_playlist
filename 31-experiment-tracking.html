Experiment Tracking, Registries & Reproducibility

Six months after a model ships, someone asks: which data was it trained on, who approved it, and can we rebuild it? If the answer involves searching Slack, you don't have an ML platform — you have a collection of notebooks that happened to work.

  • Log everything a run needs to be re-creatable
  • Use a model registry with versions, stages and approvals
  • Trace lineage from raw data to a deployed prediction
  • Choose the right level of reproducibility for the cost
  • Write a model card that answers the questions people actually ask

What a run must record

A training run is a function of many inputs. Record every one of them, automatically, or the run is not a result — it's an anecdote.

CategoryRecordWhy
CodeGit commit, diff if dirty, entry point“It worked on my branch” is not a version
DataDataset name + immutable version/snapshot id, row count, checksumThe single most commonly missing item
ConfigEvery hyperparameter, resolved (not the template)Defaults change; the resolved config is the truth
EnvironmentContainer digest, library versions, CUDA/driverA framework upgrade silently changes numerics
HardwareGPU type and count, parallelism layoutExplains throughput differences and some numeric differences
RandomnessSeeds for every library, determinism flagsDistinguishes a real gain from a lucky one
OutputsMetrics over time, final metrics per slice, artifacts, logsWhat you'll compare against next quarter
ProvenanceWho ran it, when, why (the ticket or hypothesis)Turns a run list into an experiment history
⚙️
Automatic or it won't happen

Manual logging decays within two sprints. Wrap training in a launcher that captures the commit, the resolved config, the environment digest and the dataset version without anyone remembering to. The minimum viable setup is a tracking server, an artifact store, and a rule that nothing untracked reaches production.

The model registry

A registry is the handoff between experimentation and production: a named, versioned entry per model with its artifacts, metrics, lineage and approval state.

📦

Versions

Immutable and monotonically numbered. fraud-scorer:v37 means one exact artifact, forever.

🚦

Stages

staging → shadow → canary → production → archived. Serving asks for a stage, never for a path in someone's bucket.

✅

Gates

Promotion requires eval thresholds, slice checks, a signed-off model card, and a named approver.

↩️

Rollback

The previous version stays loadable and deployable in one command. Rehearse this — a rollback you've never tested is a plan, not a capability.

🏷️
Serving should reference a version, not “latest”

Pointing production at a floating tag means a training job can change production behaviour without a deployment. Pin the version in the deployment config and change it through the same review process as code — then “what changed at 14:00?” has an answer.

The model card

A short document shipped with every production model version. It exists so that the person debugging at 2am, the reviewer six months later and the regulator next year all get the same answers.

model: fraud-scorer version: v37 stage: production owner: risk-ml@ approved: 2026-03-14 by J. Okoro (Risk) intended use Score card-not-present transactions for manual review. NOT for account closure, credit decisions or pricing. training data txn_events@2026-02-28 (18.4M rows, 2024-03 → 2026-02) labels: chargebacks confirmed ≥60 days after the transaction metrics PR-AUC 0.612 (prev 0.588) · recall@1% FPR 0.71 slices: new accounts 0.54 · EU 0.63 · mobile 0.60 limitations Weak on accounts <7 days old; labels lag 60 days, so recent fraud patterns are under-represented. Not evaluated outside EU/UK. ethical Reviewed for disparate false-positive rate across regions (max ratio 1.18). Human review required before any account action. monitoring PSI on top-20 features; weekly recall backfill as labels land; page if precision@threshold drops >15% week-over-week. rollback registry: fraud-scorer:v36 — one command, verified 2026-03-12.
🔬
Comparing runs well

Log metrics per slice, not just in aggregate, and make comparison a first-class view: sort a sweep by the metric you care about, and look at parallel-coordinate plots to see which hyperparameters actually mattered. Most sweeps show that two parameters dominate and the rest are noise — which is the information you need for the next sweep.

⚠️
Common mistakes
  • Logging metrics but not the dataset version. The most common gap, and the one that makes a run unreproducible.
  • Mutable dataset paths. s3://data/latest/ means the same run id refers to different data over time.
  • Production pointing at “latest”. Behaviour changes without a deployment and without a record.
  • Comparing runs that differ in three things. Change one variable per experiment or you learn nothing.
  • Single-seed conclusions. A 0.4% gain from one seed is usually noise; report mean ± std over three.
  • No rollback rehearsal. The first attempt should not be during an incident.
🎤
Interview drill

Warm-up: A model in production is behaving oddly. What do you need to be able to look up?

How a strong answer sounds
Which registry version is deployed and since when; the run that produced it, with its code commit, resolved config and environment digest; the dataset snapshot it trained on; its evaluation metrics including slices; who approved the promotion; and the monitoring history since deployment. With those I can tell whether behaviour changed because the model changed, the data changed, or the world changed — three very different investigations. If any of that requires asking a person, the platform has a gap worth fixing before the next incident.

Deeper: Is bit-exact reproducibility worth it?

How a strong answer sounds
Usually not for training. It requires deterministic kernels, fixed collective algorithms, a fixed data order and pinned hardware, and it costs real throughput — for a guarantee that rarely answers a question you actually have. What matters is being able to re-run and land in the same place statistically, and being able to prove provenance for audit. I would insist on determinism in two places: inference, where the same input should give the same output for debugging and caching, and small regression tests, where non-determinism makes failures unreproducible. So: statistical reproducibility plus full lineage as the default, bit-exactness only where a regulator or a specific debugging need requires it.

🧠 Key takeaways

  • Capture code, data version, resolved config, environment, hardware, seeds and outputs — automatically.
  • A registry gives immutable versions, stages, promotion gates and a tested rollback.
  • Lineage must link raw data → run → model version → deployment → prediction before you need it.
  • Aim for statistical reproducibility plus auditability; bit-exactness is rarely worth its cost.
  • Ship a model card with intended use, slice metrics, limitations, monitoring and rollback.

Check your understanding

Which missing item most often makes a run unreproducible?

Code and config are usually versioned by habit. Data is often referenced by a mutable path, so the same command produces a different model a month later.

Why should serving reference an explicit model version rather than “latest”?

Pinning makes model changes go through the same review and leaves a timestamped record — which is what makes “what changed?” answerable.

Run A scores 0.842 and run B scores 0.846, each with a single seed. What do you conclude?

Seed variance commonly exceeds that gap. One run is an observation, not a comparison.

What belongs in a model card that teams most often omit?

Those are the parts that prevent misuse — the model being applied to a population or a decision it was never evaluated for.

Which level of reproducibility is the pragmatic default for most teams?

Matching quality across seeds, with provenance recorded for audit, answers the questions people actually ask — without the throughput cost of forcing determinism everywhere.

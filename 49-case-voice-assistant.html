Case Study: Voice Assistant

A spoken assistant that has to feel like a conversation. Humans start replying about 200 ms after the other person stops talking, and they interrupt constantly. That single fact — not model quality — dictates the entire architecture: everything streams, everything is cancellable, and the hardest component is the one that decides when you have finished your sentence.

  • Budget an end-to-end turn against human conversational timing
  • Stream ASR, generation and speech synthesis so stages overlap
  • Solve endpointing — the decision that makes or breaks the feel
  • Support barge-in with echo cancellation and total cancellation
  • Evaluate a system where word error rate hides the failures that matter

🎯
Metrics

Primary: task completion per conversation — did the user get what they asked for without repeating themselves. Conversational quality: response latency at p50 and p95, false-endpoint rate (cut the user off), late-endpoint rate (awkward pause), barge-in success, and the repeat rate, which is the single best proxy for "it misheard me". Component quality: word error rate overall and on entities, TTS naturalness ratings, wake-to-first-word latency. Guardrails: cost per conversation minute, dropped-audio rate.

🗣️
The number that sets the architecture

In human conversation the gap between one person finishing and the next starting averages around 200 ms, and gaps beyond about a second read as hesitation or as the system being broken. That budget must cover endpoint detection, the last of the transcription, the model's first words, and speech synthesis — for a pipeline that in its naive form takes several seconds. Every technique in this chapter exists to overlap stages that a batch design would run in sequence.

2 · One turn, end to end

From microphone to spoken replyStep-through
  1. Acoustic echo cancellation first — without it the assistant hears its own voice and interrupts itself. Then voice activity detection to avoid streaming silence, and a low-bitrate codec. Audio leaves in 20 ms frames over a persistent connection; a request-response API cannot express a conversation.
  2. A streaming ASR model emits partial hypotheses every ~120 ms and revises them as more audio arrives. Partials are what make the rest possible: the dialogue model can begin reading the sentence before the user has finished saying it.
  3. The hardest component in the system. A pause is not the same as an ending — people pause mid-sentence to think, and stop abruptly when they are done. Combine acoustic silence with a semantic judgement of whether the transcript so far is a complete request, and adapt the threshold to context and to the speaker.
  4. Speculative start: on a likely endpoint, begin prefill against the partial transcript. If the user carries on, cancel and restart — wasted compute is much cheaper than a slow reply. Once the endpoint is confirmed, only the last few tokens need prefilling, so first output arrives in tens of milliseconds rather than hundreds.
  5. Do not wait for the full answer. Chunk the token stream at clause boundaries and synthesise each chunk as it completes. The first spoken word leaves while the model is still deciding how the sentence ends — this is the largest single latency win in the pipeline, and it is entirely a pipelining trick.
  6. Audio must never gap mid-word, so a small buffer absorbs network variance. Too large and you have simply moved the latency to the end; too small and the reply stutters, which users find far worse than a slightly later start.
  7. When the user speaks over the reply, stop playback within ~150 ms, cancel generation and synthesis, and — crucially — record how much of the reply was actually heard. The conversation history must reflect what the user experienced, not what the model produced.
  8. Transcript, resolved entities, tool results, device context and what was actually spoken. Voice sessions are long and heavily anaphoric — "that one", "the second thing" — so session state does more work here than in a text product.

4 · Deep dive: endpointing

Every other component has a benchmark. This one is judged entirely by feel, and it fails in two directions that require opposite fixes.

Too eagerThe assistant interrupts mid-sentence. Users pick this up immediately, start speaking faster and more defensively, and the experience degrades further. Most common with fixed silence thresholds under 500 ms, and with speakers who pause to think — which correlates with age, accent and cognitive load, so a global threshold is quietly unfair.
Too slowAn awkward gap after every request. Less alarming than being cut off, but it is the difference between a conversation and a kiosk, and it compounds across a multi-turn session.
Acoustic signalSilence duration, energy envelope, and prosody — a falling pitch contour is a strong completion cue, a rising one usually is not. Cheap, fast, language-dependent.
Semantic signalIs the transcript so far a complete request? “Set a timer for” is obviously unfinished; “set a timer for ten minutes” is obviously done. A small classifier over the running partial transcript, which is why partials matter beyond display.
ContextAfter a question from the assistant, wait longer — the user is composing an answer. In a dictation mode, wait much longer. Mid-list (“add milk, eggs…”) the comma prosody says more is coming.
The escape hatchSpeculative start makes eager endpointing cheap to be wrong about: begin generating, and cancel if the user continues. This converts an accuracy problem into a compute problem, and compute is the easier one to buy.
🔊
Barge-in is a distributed cancellation problem

When the user speaks over the assistant, four things must stop nearly at once: playback, synthesis, token generation, and any tool call in flight. Playback is local and easy. The rest are on a server that may be several hops away, so the cancel signal has to travel the same fast path as the audio, and the generation scheduler has to honour it — an abandoned stream that keeps decoding costs money and, worse, can deliver audio after the user has moved on.

Then there is the subtle part: the conversation history must record what the user heard, not what was generated. If the assistant produced three sentences and the user interrupted after four words, the model's next turn must be conditioned on those four words. Get this wrong and the assistant refers confidently to information it appeared to give but never actually spoke — one of the strangest-feeling bugs in a voice product, and one that no component test catches.

5 · Evaluating a voice system

LayerMeasureWhat it misses
ASRWord error rate by language, accent, noise conditionAverages hide the failures that matter — one wrong contact name ruins the turn while ten wrong filler words do not
ASR, entitiesError rate on names, numbers, addresses, app namesThe metric that actually predicts task failure; always measure it separately
EndpointingFalse-cut rate, median added delayOnly meaningful sliced by speaker and context; a global threshold is unfair to slower speakers
DialogueTask completion, tool-call correctnessText evaluations transfer poorly — spoken requests are shorter, messier and more anaphoric
TTSNaturalness ratings, pronunciation of names and numbersAverages hide the catastrophes: a mispronounced user name is remembered long after a hundred good sentences
End to endRepeat rate, abandonment, task completion per conversationThe only numbers that capture the pipeline's interactions — and the only ones worth shipping on

Evaluate on real acoustic conditions: a kitchen with a radio on, a car at speed, a phone on speaker across a room. Clean-audio benchmarks are where voice systems look finished and field recordings are where they turn out not to be.

🎤
Interview drill

Follow-up: “Users say it interrupts them. Your endpointer's false-cut rate is 2% and hasn't changed. Explain.”

How a strong answer sounds
Two percent as an average almost certainly hides a distribution. I would slice it: by speaker — some people pause mid-sentence far more, and that correlates with age, accent and speaking a non-native language, so a global silence threshold cuts off some cohorts several times more often; by context — after the assistant asks a question the user is composing, so the same threshold is too aggressive; by acoustic condition, since background noise changes what the voice activity detector sees; and by utterance type, because lists and dictation need much longer waits. I would also check whether "interrupts me" is really an endpointing complaint at all: failing echo cancellation makes the assistant barge in on itself, and a mis-tuned barge-in threshold makes background speech stop playback, both of which users describe the same way. The fix is per-cohort and per-context thresholds with an adaptive component, plus speculative start so that being eager is cheap to get wrong — and I would replace the global rate with a dashboard sliced by cohort, since the average was the thing hiding this.

Follow-up: “Would a single speech-to-speech model remove all of this complexity?”

How a strong answer sounds
It removes some of it and moves the rest. Going straight from audio to audio drops two serialisation points and can preserve tone, emotion and overlapping speech that a transcript throws away, and the latency is genuinely better. What it does not remove: endpointing and barge-in still exist, because they are properties of conversation rather than of the pipeline; you still need cancellation; and you lose the transcript as a debugging, logging and evaluation surface, which is a real operational cost — with a cascade I can tell whether a failure was mishearing or misunderstanding, and with an end-to-end model I often cannot. It is also harder to attach tools, to enforce policy on the text before it is spoken, and to support twelve languages at uneven data volumes. In practice I would run it where its strengths pay — casual conversational turns, low-latency chit-chat — and keep the cascade for anything involving tool calls, entities or compliance, which is the same tiering answer as in the other case studies.

🧠 Key takeaways

  • Human turn-taking timing sets the budget; every stage must stream so that stages overlap rather than queue.
  • Synthesising the first clause while the model is still generating is the largest single latency win available.
  • Endpointing is the hardest component, needs acoustic plus semantic signals, and must be measured per cohort — averages hide unfairness.
  • Speculative start converts an endpointing accuracy problem into a compute problem, which is the easier one to buy your way out of.
  • Barge-in is distributed cancellation, and the history must record what the user actually heard.

Check your understanding

Why synthesise speech clause by clause instead of waiting for the full response?

Pure pipelining. Nothing about the answer changes; the user simply hears it seconds earlier, which is the difference between a conversation and a kiosk.

Why is a fixed silence threshold a poor endpointer?

Combine acoustic silence with a semantic judgement of whether the request is complete, and adapt by context and speaker. A global threshold is quietly unfair to slower speakers.

What does speculative start buy you?

Around 18% of prefills are wasted, and that is a good trade: compute is easier to buy than endpointing accuracy.

After a barge-in, what must the conversation history contain?

Otherwise the assistant refers confidently to information it never spoke — a bug that feels uncanny to users and that no component test catches.

Why track entity error rate separately from word error rate?

Task success depends on names, numbers and addresses. Entity error rate predicts it; overall WER can improve while task completion falls.

Pretraining, Scaling Laws & Data Curation

Pretraining is one objective — predict the next token — applied to an enormous, ruthlessly filtered corpus. The interesting engineering is not the loss function; it's deciding how big a model to train, for how long, on which tokens, given a fixed pile of money.

  • Explain what next-token prediction actually teaches a model
  • Design a data pipeline: filter, deduplicate, mix, shard
  • Use scaling laws to pick model size and token count for a compute budget
  • Adjust that choice when inference cost matters more than training cost
  • Avoid contamination and know what “emergence” does and doesn't mean

One objective, enormous consequences

The loss is cross-entropy on the next token, computed at every position in parallel thanks to causal masking. To predict well across trillions of tokens, a model is forced to internalise grammar, facts, code semantics, arithmetic patterns, translation, style and a good deal of reasoning — because all of them reduce prediction error.

for batch in stream:                       # ~4M tokens per step at frontier scale
    logits = model(batch[:, :-1])
    loss   = cross_entropy(logits, batch[:, 1:])
    loss.backward(); clip_(1.0); opt.step(); sched.step()
🎯
Why this objective is so efficient

Every token is a labelled example, and the labels are free. A 2-trillion-token corpus gives 2 trillion supervised predictions with no annotation budget at all. That's the entire reason self-supervised pretraining scaled when supervised learning could not.

The data pipeline is the product

Raw web text is mostly unusable. Every serious pretraining effort is a filtering pipeline, and the ratio between what goes in and what survives is brutal.

Deduplication is worth more than almost anything else

Web crawls contain the same text dozens of times — mirrors, quotes, templates, scraped copies. Duplicates waste compute, encourage memorisation (a privacy and copyright hazard), and distort the data mixture. Published results consistently show deduplicated corpora reach the same loss with substantially fewer tokens. Do exact dedup first (cheap), then MinHash/LSH near-dedup (expensive but high value).

High-quality sources are usually upsampled (repeated 2–4 epochs) while web text is seen once. Repeating a small corpus too many times produces diminishing returns and eventually memorisation.

Scaling laws: how to spend a compute budget

Loss falls predictably as a power law in model size, data and compute. The practical question is how to split a fixed budget C ≈ 6·N·D between parameters N and tokens D.

Kaplan et al. (2020)

Found loss scaling smoothly with N, D and C, and suggested spending most of the budget on parameters. This is why 2020–2021 models grew enormous while token counts stayed near 300B.

Chinchilla (2022)

Corrected it: for a fixed budget, N and D should grow together — roughly 20 tokens per parameter. A 70B model on 1.4T tokens beat a 280B model on 300B tokens using the same compute.

Compute-optimal ≠ deployment-optimal

Chinchilla minimises training loss per training FLOP. If you will serve the model billions of times, inference cost dominates the total, and it is worth over-training a smaller model — 100–300 tokens per parameter — because the serving bill scales with N forever while the extra training cost is paid once. That's exactly why 7–8B models are now trained on 10–15T tokens.

Everything is decided on small models first

Nobody tunes hyperparameters at 70B. You run a ladder of small models (e.g. 70M → 300M → 1B), fit the scaling trend, and extrapolate. Data-mixture ablations, tokenizer choice and architecture changes are all validated this way. When people say “scaling laws”, day to day they mean “the tool we use to make one expensive run non-speculative”.

Emergence and contamination

✨ “Emergent” abilities

Some capabilities appear to switch on abruptly with scale. Much of that abruptness is a metric artefact: exact-match scoring turns smooth improvements into a step. Smooth metrics (log-likelihood, partial credit) usually show gradual gains — useful to know before you build a roadmap on a cliff edge.

🚨 Benchmark contamination

If the test set was on the web, it's in your corpus. Decontaminate by n-gram matching against every benchmark you'll report, keep a private held-out set, and treat any suspiciously strong public-benchmark result as contaminated until proven otherwise (Chapter 35).

⚠️
Common mistakes
  • Scaling parameters without scaling data. A big model on too few tokens is undertrained and expensive to serve — the pre-Chinchilla error.
  • Skipping near-duplicate removal. You pay full compute for repeated text and increase memorisation risk.
  • Filtering so hard that you delete the long tail. Aggressive quality classifiers strip dialects, minority languages and technical jargon, and the model's coverage narrows.
  • Reporting benchmarks without decontamination. The number is meaningless and someone will find out.
  • Tuning on the big run. Establish hyperparameters on a ladder of small models; the big run is for execution, not exploration.
  • Forgetting the data licence. Provenance is a legal requirement at this scale, not a nicety (Chapter 37).

Interview drill

Warm-up: You have compute for either a 30B model on 600B tokens or a 7B model on 2.6T tokens. Which do you pick?

How a strong answer sounds
Both are roughly the same training FLOPs. Chinchilla says the compute-optimal split is around 20 tokens per parameter, so 30B/600B and 7B/2.6T are respectively at 20 and 370 tokens per parameter — the first is compute-optimal, the second is heavily over-trained. If this is a research artefact and training loss is the goal, take the 30B. If it will be served at scale, take the 7B: it costs roughly 4× less per generated token forever, fits on smaller hardware, and the quality gap after over-training is small. The deciding question is the ratio of inference volume to training cost.

Deeper: Your pretraining loss is fine but downstream code ability is weak. What do you investigate?

How a strong answer sounds
Loss is dominated by the majority of the mixture, so a weak minority domain barely moves it — I'd compute per-domain held-out loss rather than the aggregate. Then check the mixture share of code and whether aggressive quality filters stripped repositories; check the tokenizer's handling of indentation and identifiers, since a code-hostile vocabulary costs both context and accuracy; check dedup didn't remove near-identical but legitimate code files wholesale; and consider a mid-training phase that upsamples high-quality code. I'd validate each hypothesis on a small-model ablation before touching the main run.

🧠 Key takeaways

  • Next-token prediction turns unlabelled text into trillions of free supervised examples.
  • Most of pretraining engineering is filtering, deduplicating and mixing data — not the loss.
  • Chinchilla: for a fixed budget, grow parameters and tokens together, roughly 20 tokens per parameter.
  • If inference volume is large, over-train a smaller model — serving cost scales with N forever.
  • Decide architecture and hyperparameters on a ladder of small models; decontaminate before reporting anything.

Check your understanding

What did the Chinchilla result change?

Before it, budgets went disproportionately into parameters. Chinchilla showed those models were undertrained: the same compute spent on a smaller model and more tokens produced a better model.

Why is near-duplicate removal so valuable in a pretraining corpus?

Repeated text is paid for at full price, encourages verbatim memorisation (a privacy and copyright risk), and silently upweights whatever happens to be duplicated most.

You will serve a model to 100M users daily. How should that change the Chinchilla-optimal choice?

Inference cost is proportional to parameters and is paid on every request forever. Over-training a smaller model shifts cost into the one-off training bill.

Your model scores suspiciously well on a public benchmark. Most likely explanation?

Public benchmarks are on the web, therefore in the crawl. Run n-gram decontamination and re-check on a private held-out set before believing the number.

How are hyperparameters for a 70B pretraining run usually chosen?

Full-scale search is unaffordable. You fit scaling trends on 70M–1B models, extrapolate, and use the big run for execution rather than exploration.

MLOps: CI/CD/CT Pipelines

Software CI answers “does this code still work?”. ML has three moving parts — code, data and model — and any one of them can break the system while the other two look fine. That's why there's a third letter: continuous training.

  • Design a test suite that catches ML-specific failures
  • Build a CI pipeline that's fast enough that people keep it
  • Choose retraining triggers and the guardrails around them
  • Promote models through environments with automated gates
  • Place your team honestly on the maturity ladder

Three things change, not one

💻

Code

Feature transforms, training script, serving handler. Tested like any software — and it must be the same transform code in both paths (Chapter 29).

🧱

Data

Changes continuously without a deploy. Needs contracts, validation and distribution checks in the pipeline itself (Chapters 3, 28).

🧠

Model

A learned artefact whose behaviour can regress on a slice while aggregate metrics improve. Needs behavioural tests and slice gates.

CI has to be fast or it gets bypassed

Keep the per-commit path under ten minutes: unit tests, a data-validation run on a fixed sample, and a tiny training smoke test with a fixed seed. Push full training, full eval and load tests to a nightly or pre-promotion pipeline. A twenty-minute CI becomes a skipped CI, and a skipped CI is worse than none because it creates false confidence.

Continuous training

Models decay because the world moves (Chapter 34). Retraining should be an automated, gated pipeline — not a quarterly project someone remembers.

🚧
Automated retraining without gates is an automated outage

A pipeline that trains and deploys on a schedule will eventually train on a corrupted upstream table and ship it at 3am. Every automatic promotion needs: data validation that fails closed, a comparison against the current production model on a frozen eval set, slice checks, a parity test, and a canary with automatic rollback. If any gate can't be evaluated, the pipeline stops and pages someone — it does not proceed.

Environments and promotion

dev        → developer machines and notebooks, sampled data, no gates
staging    → full pipeline on real data, artifacts written to a staging registry
shadow     → production traffic, model runs, output logged but not used
canary     → 1–5% of real traffic, automatic rollback on guardrail breach
production → full traffic, pinned version, previous version kept warm
🪞
Shadow mode is the cheapest safety net in ML

Run the new model on real production traffic, log its outputs, and act on none of them. It catches serving-time feature skew, latency regressions, unexpected input distributions and crash-inducing edge cases — all the things offline evaluation cannot see — with zero user risk. A few days of shadow before every canary should be routine.

The maturity ladder

Level 0Manual. A notebook produces a model; someone copies a file to a server. Works for one model and one person, and nothing about it survives that person leaving.
Level 1Reproducible training. Training is a script in version control, run on a schedule, logging to a tracker. Deployment is still manual, but you can rebuild the model.
Level 2Automated pipeline. Data validation, training, evaluation and registration run as one orchestrated DAG. Promotion is a human decision informed by automated gates.
Level 3Continuous training with gates. Triggers fire retraining; gates and canaries decide promotion; rollback is automatic. Humans review exceptions rather than routine releases.
Level 4Platform. Multiple teams ship models through shared, self-service infrastructure with standard monitoring, governance and cost attribution (Chapter 39).

Most teams should aim for level 2–3. Level 4 is a product in its own right, and building it before you have several models in production is a way to avoid shipping one.

⚠️
Common mistakes
  • Testing code but not data. Most ML incidents start upstream of your repository.
  • Gates on aggregate metrics only. A model that improves overall and destroys one slice passes — and that slice is someone's whole experience.
  • Automated promotion without a canary. Offline gates predict the online result; they don't guarantee it.
  • CI that takes 40 minutes. It gets skipped, and the skip becomes policy.
  • No fail-closed rule. When validation can't run, pipelines that continue anyway ship whatever happened to be there.
  • Retraining because it's Tuesday. Retrain when the data or the world justifies it, and always compare against the incumbent.

Interview drill

Warm-up: What does a CI pipeline for an ML repo test that a normal one doesn't?

How a strong answer sounds
Data and model behaviour. Data: schema, ranges, null rates, volume and freshness against a contract, so an upstream change fails fast. Model: a tiny training smoke test that must reduce loss and produce a loadable artifact; behavioural tests — invariance, directional expectations, and known-case checks; and, before promotion, slice-level comparison against the incumbent plus a train/serve parity check. Ordinary software tests still apply to the transform code — and crucially, the same transform code must be used in training and serving, which is itself something to assert in CI.

Deeper: Design a safe automatic retraining pipeline for a fraud model with 60-day label lag.

How a strong answer sounds
Trigger on a combination: a weekly schedule, plus drift on input distributions, plus a proxy-metric alarm — because true labels are 60 days late, so performance-based triggers alone react two months too slowly. The pipeline validates data and fails closed; builds the training set with point-in-time joins and a label cut-off that respects the lag; trains; evaluates against a frozen eval set and the incumbent, on aggregate and on slices; runs a parity check between offline and online features; registers the candidate. Promotion goes shadow for a few days, then canary at 5% with automatic rollback on precision-at-threshold or false-decline guardrails, then full. Labels arriving later backfill the evaluation so I can measure, retrospectively, whether each promotion was actually right — and that record is what tunes the trigger thresholds over time.

🧠 Key takeaways

  • Code, data and model each change independently; the pipeline must test all three.
  • Keep per-commit CI under ten minutes; push heavy evaluation to pre-promotion stages.
  • Retraining needs triggers and gates — validation that fails closed, incumbent comparison, slices, canary.
  • Shadow mode catches serving-time problems offline evaluation cannot, at zero user risk.
  • Aim for maturity level 2–3; a platform is justified by several models, not by ambition.

Check your understanding

Which test would catch “an upstream team renamed a column and the feature is now all nulls”?

The model still trains and still serves — only the data changed. Only data validation fails loudly at the right moment.

What is shadow mode?

It exposes the candidate to genuine production inputs — including skew, latency and edge cases — with no user impact, before any traffic depends on it.

Your automatic retraining pipeline shipped a broken model at 3am. What was almost certainly missing?

Automation without gates just makes mistakes faster. Every promotion needs conditions that can block it and a rollback that runs without a human.

Why is a performance-based retraining trigger insufficient when labels arrive 60 days late?

With delayed labels you need leading indicators — input drift, prediction-distribution shift and proxy metrics — combined with a schedule.

A promotion gate uses only aggregate AUC. What can slip through?

A 4-point gain overall can hide a 20-point loss for new users. Gates must include per-slice comparisons against the incumbent.

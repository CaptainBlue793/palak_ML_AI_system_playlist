Hardware: GPUs, Memory & the Roofline

Modern ML performance is rarely about FLOPs. It's about whether the data reaches the arithmetic units fast enough. Once you can tell a memory-bound kernel from a compute-bound one, most “why is my GPU at 30%?” questions answer themselves.

  • Describe what a GPU is actually good at, and why
  • Read the memory hierarchy and its bandwidth numbers
  • Compute arithmetic intensity and place a kernel on the roofline
  • Explain why LLM decoding is memory-bound and training is not
  • Pick numeric precisions and understand interconnect limits

CPUs think, GPUs sweat

A CPU core is a brilliant generalist: deep pipelines, big caches, branch prediction, optimised for finishing one chain of dependent work quickly. A GPU is thousands of simple lanes doing the same instruction on different data. Deep learning is almost entirely “multiply these giant matrices”, which is exactly that shape.

🧠 CPU

~8–128 fat cores · huge caches · ~0.5–2 TFLOP/s fp32 · ~100–400 GB/s memory. Optimised for latency on branchy, irregular code.

🎮 GPU

~100+ streaming multiprocessors · thousands of threads · ~100–2,000 TFLOP/s in low precision · 2–8 TB/s HBM. Optimised for throughput on regular, parallel work.

🚚
Analogy: sports car vs freight train

A sports car gets one parcel across town fastest. A freight train moves ten thousand parcels per trip but takes an hour to load. If your workload is one small parcel at a time — an LLM generating a single token for a single user — you're running a freight train nearly empty. Batching is how you fill it (Chapter 26).

Inside the chip

The important parts, in the order they matter for performance:

Tensor coresDedicated matrix-multiply-accumulate units. They provide nearly all of a modern GPU's advertised FLOPs — and only for matmul-shaped work in supported precisions. An elementwise kernel never touches them.
Registers / SMEMTens of KB per block, terabytes/s, one-cycle-ish latency. Kernel authors fight to keep data here (this is what FlashAttention is about).
L2 cache~40–60 MB, several TB/s. Shared across the chip; the difference between a fused and an unfused operation is often just whether data stayed in L2.
HBM (VRAM)40–192 GB at 2–8 TB/s. Huge compared to caches, tiny compared to your dataset, and the usual bottleneck.
NVLink / PCIeGPU-to-GPU: NVLink ~400–900 GB/s; PCIe 5 ~64 GB/s. An order of magnitude slower than HBM — which is why model sharding strategy is a systems design problem (Ch 24).
NetworkInfiniBand/Ethernet at 100–400 Gb/s per NIC (~12–50 GB/s). Two more orders of magnitude down. Multi-node training lives or dies on how little you send here.
📉
The gap that defines modern ML performance

Compute has grown far faster than memory bandwidth for two decades. An H100-class GPU can do roughly 300–500 arithmetic operations in the time it takes to fetch one number from HBM. So the question for any kernel is not “how many FLOPs?” but “how many FLOPs per byte moved?”

Arithmetic intensity and the roofline

Arithmetic intensity (AI) = FLOPs performed ÷ bytes moved from memory. Plot achievable throughput against AI and you get the roofline: a diagonal region where you're limited by bandwidth, and a flat region where you're limited by the arithmetic units.

Reference device: ~990 TFLOP/s bf16 dense, 3.35 TB/s HBM (H100-class). The ridge point — where the diagonal meets the ceiling — is around 295 FLOPs/byte. Any kernel below that number cannot reach peak compute no matter how well it is written.

🧮
Why decoding one token is so inefficient

Generating a token requires reading every weight of the model from HBM and doing roughly two FLOPs per weight. That's an arithmetic intensity of about 2 — a hundred times below the ridge point. The GPU spends its time waiting on memory, using a small fraction of its arithmetic units. Batch 64 requests together and you read those same weights once for 64 tokens: intensity ≈ 128, and throughput improves almost linearly. That single fact drives the entire design of inference servers.

Lower precision is usually a bandwidth optimisation

Halving the bits halves the bytes you move. For memory-bound work (decoding, elementwise, small batches) that's close to a 2× speedup even if the arithmetic units were never the limit. This is why int4 weight-only quantization speeds up single-user LLM serving so dramatically.

Utilization: MFU and why you're at 30%

Beyond one GPU, and beyond NVIDIA

🔗

Topology matters

8 GPUs on one node share fast NVLink; crossing nodes drops to network speed. Parallelism strategies are chosen to keep the chattiest communication inside a node (Ch 24).

🧊

TPUs

Systolic-array accelerators with big on-chip memory and a fast 2D/3D torus interconnect. Excellent at dense matmul at scale; programmed through XLA, so kernel-level control is different, not absent.

💻

CPU inference

Perfectly viable for small models, GBDTs and low-QPS services. Quantized 7B models run on laptops. Don't pay for a GPU to serve 12 requests a minute.

⚠️
Common mistakes
  • Optimising FLOPs when you're memory-bound. A cleverer algorithm with the same bytes moved changes nothing. Measure intensity first.
  • Assuming peak TFLOPs are reachable. Vendor numbers assume ideal dense matmul in the lowest precision, often with sparsity. Real MFU of 40% is healthy.
  • Ignoring the data pipeline. The most common cause of an idle GPU is a CPU that can't decode JPEGs or tokenize fast enough.
  • Buying the biggest GPU for a small model. If the model fits in 24 GB and you're latency-bound, more HBM does nothing; bandwidth and clocks do.
  • Forgetting activation memory. Weights fit; then the first batch OOMs. Activations scale with batch × sequence × layers (Ch 23).
🎤
Interview drill

Warm-up: Why does batching help LLM inference so much more than it helps image classification?

How a strong answer sounds
Autoregressive decoding reads the entire weight matrix to produce a single token, so arithmetic intensity is about 2 FLOPs/byte — deeply memory-bound. Batching amortises that weight read across many sequences, so throughput scales almost linearly until you approach the compute roof or run out of KV-cache memory. A CNN forward pass on a 224×224 image already does thousands of FLOPs per byte of weights, so it sits near the compute roof even at batch 1 — extra batching helps far less.

Deeper: Your training run reports 95% GPU utilization but only 18% MFU. What's going on?

How a strong answer sounds
Utilization only says a kernel was resident, not that it was doing useful matmul. 95% util with 18% MFU means the GPU is busy running many small, memory-bound kernels — elementwise ops, normalizations, unfused attention, dtype casts — rather than tensor-core work. I'd profile to get a kernel-time breakdown, fuse with torch.compile or custom kernels, switch to flash attention, raise the batch size or sequence packing to increase intensity, and check I'm not silently running in fp32. If a lot of time is in all-reduce, the fix is overlapping communication with the backward pass instead.

🧠 Key takeaways

  • GPUs trade latency for throughput; they win only on regular, parallel, matmul-shaped work.
  • Arithmetic intensity (FLOPs per byte) decides whether a kernel is memory- or compute-bound.
  • LLM decoding at batch 1 is extremely memory-bound — batching is the primary throughput lever.
  • Training memory is weights + gradients + optimizer state + activations; the optimizer often dominates.
  • MFU of 35–55% is good; low MFU usually means data loading, unfused kernels or unoverlapped communication.

Check your understanding

A kernel has arithmetic intensity of 3 FLOPs/byte on a device with a ridge point of 295. It is…

Far below the ridge point means the arithmetic units are starved. The levers are moving fewer bytes (fusion, lower precision, caching) or reusing each byte more (bigger batches).

Which change most improves throughput for batch-1 LLM decoding?

The bottleneck is reading weights from HBM. Quartering the bytes roughly quarters the read time; extra FLOPs go unused because the arithmetic units are already idle waiting.

Training a 7B model with AdamW in mixed precision. Which is typically the single largest memory consumer?

Adam keeps two fp32 moments plus an fp32 master copy — roughly 12 bytes per parameter versus 2 for bf16 weights. That's the arithmetic that motivates ZeRO sharding in Chapter 23.

GPU utilization shows 40% with visible gaps between steps. What do you investigate first?

Periodic gaps are the signature of a starved GPU: not enough loader workers, slow decoding, or no prefetch. Check that before touching anything about the model.

Why is bf16 generally safer than fp16 for training?

Range matters more than precision for gradients. bf16's wide exponent removes the need for loss scaling and the class of NaN failures that comes with fp16.

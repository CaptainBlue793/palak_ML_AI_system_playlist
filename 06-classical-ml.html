Classical ML: Trees & Ensembles

Deep learning owns text, images and audio. On the spreadsheet-shaped data that runs most businesses, gradient-boosted trees are still the model to beat — and the model you should build first, because they're fast, robust and almost free to serve.

One question at a time

A decision tree is a flowchart the machine writes. At each node it picks one feature and one threshold that best separate the classes, then recurses on each side. Prediction is walking from the root to a leaf and reading off the majority class (or the mean value).

“Best” needs a score. The usual one is Gini impurity — the probability that two randomly drawn items from a node have different labels:

Gini = 1 − Σ pₖ²        # 0 = pure node, 0.5 = fifty-fifty (binary)
gain = Gini(parent) − weighted average Gini(children)

The tree tries every feature and every candidate threshold, and keeps the split with the largest gain. That's the entire training algorithm — a greedy search, repeated.

🩺
Analogy: triage questions

A nurse doesn't ask 40 questions in a fixed order. They ask the one that splits the possibilities fastest — “are you in pain?” — then branch. A tree is that instinct, made numerical: at every point, ask the question that separates the outcomes best.

A single deep tree always overfits

Grow it far enough and every training point gets its own leaf: 100% training accuracy, and a boundary that memorises noise. The fix isn't a better splitting rule — it's many trees, which is where ensembles come in.

Bagging: average away the variance

A random forest trains hundreds of deep trees, each on a bootstrap sample of the rows and a random subset of the features at each split, then averages their votes. Each tree is individually overfitted, but their errors are partly independent — so averaging cancels much of the noise while keeping the signal.

Why the randomness matters

If every tree saw the same data and features, they'd be nearly identical and averaging would achieve nothing. Row sampling (bagging) plus column sampling decorrelates them, and decorrelation is exactly what makes the average better than the parts.

Free validation

Each tree leaves out ~37% of rows (the out-of-bag sample). Scoring each row with only the trees that never saw it gives an honest estimate without a separate holdout — handy when data is scarce.

Boosting: fix your own mistakes, repeatedly

Gradient boosting takes the opposite approach. Instead of many strong independent trees, it builds many weak trees in sequence, where each one is fitted to the residual errors of everything built so far. Step through it:

The three libraries you'll actually use

⚡

XGBoost

The one that popularised GBDT competitively. Level-wise growth, strong regularization, excellent docs, runs everywhere.

🌿

LightGBM

Histogram binning plus leaf-wise growth: much faster on wide/large data. Usually the default today. Watch overfitting on small datasets.

🐈

CatBoost

Native categorical handling with ordered target statistics that avoid the leakage of naive target encoding. Strong out-of-the-box defaults.

🎚️
The hyperparameters worth your time
  • learning_rate + n_estimators — set the rate low (0.03–0.1) and let early stopping choose the number of trees.
  • max_depth / num_leaves — capacity per tree. The main overfitting knob.
  • min_child_samples — refuse leaves built from a handful of rows; crucial on imbalanced data.
  • subsample + colsample_bytree — stochasticity; both regularizes and speeds training.
  • reg_lambda — L2 on leaf values. Cheap insurance.

Everything else is a rounding error compared with better features.

Three traps in that chart
  • Split-count importance favours high-cardinality features. A continuous column offers thousands of thresholds, so it wins on count without being more useful. Prefer gain-based or permutation importance.
  • Correlated features share credit arbitrarily. Two near-duplicate columns each look half as important as either would alone — and dropping “the unimportant one” can cost you nothing or everything.
  • Importance is not causation. It says the model used it, not that changing it changes the outcome. SHAP values explain the model's behaviour — still not the world's.

🚀
Trees are a joy to serve

No GPU, no batching, a model file measured in megabytes, and inference that's a few hundred branch comparisons. Latency is microseconds and deployment is “copy a file”. When you're weighing a 0.3% accuracy gain from a neural ranker against this, count the serving bill too (Chapter 38).

⚠️
Common mistakes
  • One-hot encoding a 50,000-value column for a tree. Each binary column is a weak split; trees choke. Use native categorical support or target/ordinal encoding instead.
  • Standardizing inputs for trees. Harmless but pointless — splits are threshold comparisons, so monotone rescaling changes nothing.
  • Tuning n_estimators by hand. Set the learning rate, then let early stopping on a validation set pick the count.
  • Assuming a random forest can't overfit. It resists it, but with noisy labels and deep trees it absolutely can.
  • Extrapolating. A tree can never predict outside the range of the target it saw. For trends that grow, model the trend explicitly or use a linear component.

Interview drill

Warm-up: Why does a random forest generally beat a single deep tree?

How a strong answer sounds
A single deep tree has low bias and very high variance — small changes in the data produce a completely different tree. Averaging many trees trained on bootstrapped rows with random feature subsets keeps the low bias while cancelling much of the variance, because the trees' errors are only partly correlated. The randomness is the point: identical trees would average to the same overfitted model.

Deeper: You're asked to justify choosing LightGBM over a deep neural network for a 3-million-row fraud model.

How a strong answer sounds
On mixed-type tabular data with heavy class imbalance, GBDT typically matches or beats a tuned MLP with a fraction of the effort, handles missing values and outliers natively, and needs no scaling. It trains in minutes on CPU, so we can retrain daily as fraud patterns shift; the serving model is a few megabytes and runs in microseconds inside a 10 ms budget with no GPU cost. I'd still use embeddings from a neural component for high-cardinality entity IDs and graph signals if evaluation shows they add lift — but the default should be the model that gets a trustworthy baseline into production this week, with the NN as the challenger.

🧠 Key takeaways

  • A tree greedily picks the split with the biggest impurity reduction; depth controls overfitting.
  • Random forests reduce variance by averaging decorrelated deep trees; boosting reduces bias by sequentially fitting residuals.
  • Tune learning rate, depth, min-samples and subsampling — and let early stopping choose the tree count.
  • Feature importance is about the model, not the world; correlated features split credit unpredictably.
  • GBDT remains the first thing to try on tabular data, and it is cheap and delightful to serve.

Check your understanding

What does a decision tree maximise when choosing a split?

It tries candidate thresholds and keeps the one whose children are purest, weighted by their size. Margins belong to SVMs, not trees.

Which is the key difference between bagging and boosting?

That dependency is also why boosting needs careful tuning and early stopping, while bagging is forgiving — and why bagging parallelises trivially and boosting doesn't.

You lower the GBDT learning rate from 0.3 to 0.05. What else must change?

Each tree now contributes less, so you need roughly proportionally more of them. Lower rate + more trees usually generalises better, at the cost of training time.

Your tree model must predict energy demand that grows year on year. What's the catch?

A leaf predicts a constant learned from training data, so next year's higher demand is simply unreachable. Model the trend separately (e.g. predict the ratio to a trend line) or add a linear component.

A feature shows high split-count importance in your forest. What can you conclude?

Continuous or high-cardinality columns offer many candidate thresholds and are chosen often. Use gain-based or permutation importance, and verify by actually removing the feature and re-scoring.

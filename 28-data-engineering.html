Data Engineering & Streaming for ML

Models are downstream of pipelines. Whether a feature is available in 50 milliseconds or 6 hours, whether a backfill reproduces history exactly, and whether a schema change breaks training silently — these decide more about your ML system's reliability than the model does.

  • Choose between batch and streaming for a given feature
  • Reason about event time, windows, watermarks and late data
  • Build pipelines that are idempotent and safely re-runnable
  • Use data contracts and schema evolution to stop silent breakage
  • Budget end-to-end freshness from event to prediction

Batch or streaming?

The honest default is batch. Streaming is strictly more complex — ordering, late data, state, exactly-once semantics — and you should adopt it only where freshness changes a decision.

FeatureFreshness neededRight pipeline
“User's lifetime order count”HoursNightly batch — cheap, simple, reproducible
“Items viewed in this session”SecondsStreaming, or computed from the request payload itself
“Card's transaction count in the last 10 minutes”SecondsStreaming — the fraud signal is the recency (Chapter 44)
“Product's 30-day average rating”DailyBatch
“Driver's current location”Sub-secondNot a pipeline — read it live at request time

The shape of a modern stack

Events land in a log (Kafka/Kinesis/PubSub). A stream processor computes real-time aggregates into an online store; the same events are also written to object storage as open table formats (Iceberg, Delta, Hudi) that give you ACID commits, time travel and schema evolution on cheap storage. Batch jobs and the warehouse read those tables; an orchestrator (Airflow, Dagster) runs the DAG with dependencies, retries and backfills. CDC replicates operational databases into the same lake so the model can use transactional data without querying production.

Event time, windows and late data

The moment something happened and the moment your system saw it are different — sometimes by milliseconds, sometimes by hours when a phone was offline. Aggregating by processing time is easy and wrong; aggregating by event time is correct and requires you to decide how long to wait.

The watermark is a correctness/latency dial

A long watermark waits for stragglers and produces complete results slowly. A short one is fast and drops late data. Neither is “right” — pick from the decision downstream. For fraud scoring, being 30 seconds late is worse than missing 0.3% of events; for billing aggregation the reverse is true, so you emit early results and correct them later with an update path (and make every consumer idempotent so corrections are safe).

Delivery semantics

1️⃣

At-most-once

Never duplicated, sometimes lost. Acceptable only for metrics you can afford to miss.

🔁

At-least-once

Never lost, sometimes duplicated. The practical default — pair it with idempotent consumers and duplicates stop mattering.

🎯

Exactly-once

Achieved with transactional sinks and offset commits, or by deduplicating on an event id. Real, but it costs throughput and complexity — ask whether idempotency is enough first.

Backfills: the thing you'll do constantly

A new feature needs three years of history. A bug means last month's aggregates are wrong. A model needs retraining on corrected data. Backfilling is routine, so design for it from the start.

PropertyWhy it matters
Idempotent writesRe-running a partition must replace, not append. Use partition overwrite or merge-on-key, never blind insert.
Partitioned by event dateLets you reprocess one day without touching the rest — the unit of both cost and blast radius.
Deterministic logicNo now(), no random seeds, no dependence on a mutable lookup table. Otherwise a backfill produces different numbers than the original run did.
Point-in-time inputsA backfill must use the state as of that day, not today's — the single most common source of training/serving skew (Chapter 29).
Throttled and observableA 3-year backfill can swamp the cluster the live pipeline shares. Rate-limit it and track progress.
🕰️
The classic backfill bug

You backfill “customer's account tier” for 2024 using today's tier table. Customers who upgraded in 2025 now appear premium throughout 2024 — so the model learns that premium customers were buying more, when actually buying more is what made them premium. The offline metric improves and the online result doesn't. Any dimension that changes over time must be stored as a slowly-changing dimension with validity ranges, and joined as of the event timestamp.

Data contracts

A pipeline breaks when an upstream team renames a column on a Tuesday. A data contract makes the schema and its guarantees explicit, versioned and testable in the producer's CI — so the break happens in their pull request, not in your training run.

contract: checkout.completed version: 3 owner: payments-team sla: p99 < 60s to the lake fields: event_id string required unique occurred_at timestamp required event time, UTC user_id string required pseudonymised amount_minor int64 required >= 0 currency enum required [GBP, EUR, USD] coupon_code string optional nullable, may be added to guarantees: - at-least-once delivery, deduplicate on event_id - additive schema changes only within a major version - breaking changes require a new topic and 90 days of dual-write quality: - null_rate(user_id) == 0 - daily_volume within ±30% of the 7-day median

Where the money goes in a data platform

Not compute — small files and repeated scans. Thousands of tiny files per partition make every query slow and expensive; the fix is compaction and sensible partition sizing (aim for files of 128 MB–1 GB). After that: lifecycle policies to move cold data to cheaper tiers, columnar formats with predicate pushdown so queries read only what they need, and materialising the aggregates that many jobs recompute independently.

⚠️
Common mistakes
  • Aggregating by processing time. Results change when a consumer lags, and a backfill produces different numbers than the live run.
  • Non-idempotent writes. A retried job double-counts, and nobody notices until a metric looks odd weeks later.
  • Using current dimension values in a backfill. Leakage of the future into the past — the classic silent quality killer.
  • No data contract. Upstream renames a field; training silently trains on nulls.
  • Streaming everything. Most features do not need it, and each streaming pipeline is a permanent operational commitment.
  • Ignoring small files. The most common cause of a lake that gets slower and more expensive every month.

Interview drill

Warm-up: Why prefer event time over processing time for feature aggregation?

How a strong answer sounds
Because event time is a property of the data and processing time is a property of your infrastructure. If a consumer lags or you replay history, processing-time windows produce different results for the same events — so training data and serving features stop agreeing, and backfills don't reproduce. Event time makes the computation deterministic; the price is that you must handle late arrivals explicitly with watermarks and an update path for corrections.

Deeper: A model needs “transactions in the last hour” both online at 20 ms and offline for 2 years of training data. How do you build it?

How a strong answer sounds
One definition, two execution paths, with equality enforced by a test. Online: a stream processor maintains a sliding one-hour count keyed by card, written to a low-latency store the model reads at request time. Offline: the same aggregation expressed over the event log with a strict as-of join — for each labelled example, count events in the hour strictly before that example's timestamp, which is the point-in-time correctness problem of Chapter 29. I'd generate the training set from the same event stream rather than from the online store's current values, define the aggregation once in a feature repository so both paths share it, and add a continuous check comparing online values against a recomputation on a sample. Late events get a watermark and an update path, and the training set is built with the same lateness policy the online system has — otherwise offline looks better than production, every time.

🧠 Key takeaways

  • Use batch unless freshness changes a decision; streaming is a permanent operational commitment.
  • Aggregate on event time with an explicit watermark, and decide the late-data policy from the downstream decision.
  • Prefer at-least-once delivery with idempotent consumers over chasing exactly-once.
  • Design for backfills: partitioned, idempotent, deterministic, and joined as-of the event time.
  • Data contracts move breakage from your training run to the producer's pull request.

Check your understanding

What does a watermark represent in stream processing?

It is the system's assertion about completeness, and it's what lets a window close and emit. Longer watermark = more complete results, later.

You backfill “customer tier” for 2024 using the current tier table. What's wrong?

Customers who upgraded later appear upgraded throughout history. The model learns an effect backwards, and the online result never matches the offline one.

Your stream sink is at-least-once. What's the pragmatic way to handle duplicates?

Idempotency makes duplicates harmless and is far cheaper than end-to-end exactly-once machinery.

Which feature genuinely needs a streaming pipeline?

Recency is the signal itself — a five-minute-old view of a velocity feature is useless for fraud. The others tolerate hours of staleness.

What is a data contract primarily for?

It shifts the failure left: a breaking change fails the producer's build instead of silently corrupting your training set weeks later.

The Deep Learning Stack

Between loss.backward() and electrons moving on a die there are five layers of machinery. Knowing what each one does is what separates “the model is slow” from “we're launching 40,000 tiny kernels and the fix is one decorator”.

  • Name every layer from framework call to GPU kernel
  • Read a tensor's shape, stride, dtype and device — and know when a view is free
  • Explain reverse-mode autodiff and what the graph actually stores
  • Decide between eager and compiled execution, and spot graph breaks
  • Diagnose an input-bound pipeline and an out-of-memory crash

Five layers, top to bottom

Step through what happens when you run one training step.

From Python to siliconStep-through
  1. In eager mode this is ordinary Python: attribute lookups, a loop over modules, one framework call per operation. Python overhead is real — a few microseconds per op — which is invisible for big matmuls and disastrous for thousands of tiny ones.
  2. Each op is routed by dtype, device and layout to an implementation, and (if gradients are needed) an entry is pushed onto the autograd tape recording how to reverse it.
  3. With torch.compile or JAX's jit, the sequence of ops is traced into a graph, then optimised: fuse elementwise chains, pick layouts, pre-plan memory, and generate new kernels (often via Triton).
  4. A matmul lands in cuBLAS; a convolution in cuDNN; attention in FlashAttention. These are hand-tuned per architecture and per shape — which is why odd tensor sizes can be much slower than round ones.
  5. Thread blocks are scheduled onto SMs, data streams from HBM through L2 into registers, tensor cores accumulate. Everything in Chapter 10 applies here.
  6. Calling .backward() walks the tape backwards, running each op's gradient kernel. Saved activations are read here — which is why they occupy memory for the whole forward pass.
  7. Weights and optimizer state update. Naively this is thousands of tiny kernels; production implementations use fused or foreach optimizers that batch them into a handful.

Four things to check on any tensor bug

t.shape (is the batch dimension where you think?), t.dtype (silent fp32 costs 2× memory and speed), t.device (a stray CPU tensor forces a synchronising copy every step), and t.is_contiguous() (some kernels quietly fall back to a slow path or copy).

Autodiff: the tape

Frameworks use reverse-mode automatic differentiation. During the forward pass, every operation records itself and saves whatever it needs for its own derivative. backward() walks that record in reverse, applying the chain rule.

x = torch.randn(4, 3, requires_grad=True)
y = (x @ W).relu()        # saves: x, W, and the relu mask
loss = y.mean()

loss.backward()           # walks the tape backwards, fills .grad
opt.step(); opt.zero_grad()   # update, then clear — forgetting this accumulates

💾 Why activations dominate memory

Every saved intermediate must live until its backward runs — i.e. the whole forward pass. Gradient checkpointing trades compute for memory: drop most activations and recompute them during backward (~30% slower, several times less memory).

🚫 no_grad / inference_mode

At inference there is no tape to build. Wrapping evaluation in torch.no_grad() (or inference_mode) removes that memory and overhead entirely. Forgetting it is a classic cause of OOM during validation.

✂️ detach()

Cuts the graph at a point — useful for target networks, stop-gradients and logging. Accidentally keeping a tensor attached is how “my loss list ate 40 GB” happens.

Eager vs compiled

Eager execution runs operations one at a time as Python reaches them: easy to debug, and it pays Python overhead plus a memory round-trip for every op. Compilation captures a graph first and optimises across operations.

Graph breaks and recompiles

A compiler traces until it hits something it can't handle — a print, a data-dependent if, a .item() call that forces a sync. It then splits the graph, losing fusion across the boundary. Similarly, every new input shape can trigger a fresh compile: with variable-length sequences, bucket your lengths or mark dimensions dynamic, or you'll spend the run compiling.

The input pipeline is part of the model

A GPU that finishes a step in 80 ms needs the next batch ready in 80 ms. Decoding JPEGs, tokenizing text or reading many small files from network storage will not keep up unless you engineer it.

When it breaks: profiling and OOM

🔬 Profile before optimising

The framework profiler gives a kernel-level timeline: how long each op took, how much time is Python, where the gaps are. Look for (1) gaps = input starvation, (2) many tiny kernels = fusion opportunity, (3) big all-reduce blocks = communication not overlapped.

💥 OOM triage, in order

Reduce batch size → enable gradient checkpointing → check for tensors accidentally kept alive (loss lists, caches) → confirm no_grad at eval → use a memory-efficient optimizer → then shard across GPUs (Ch 23). Memory snapshots show which tensors are resident, not just the total.

📦
Checkpoints: prefer safetensors

Classic pickle-based checkpoints execute arbitrary code on load — a genuine supply-chain risk when downloading weights (Chapter 36). safetensors is a plain tensor container: no code execution, memory-mappable, faster to load. Also save the optimizer state, the RNG state, the step count and the config, or your “resume” is a restart.

⚠️
Common mistakes
  • Calling .item() or .cpu() inside the training loop. Each one synchronises the GPU and stalls the pipeline. Accumulate on device, log occasionally.
  • Keeping the loss tensor in a list. It holds the entire graph alive. Append loss.detach().item() instead.
  • Evaluating without no_grad. Doubles memory for no reason and often OOMs at the worst moment.
  • Benchmarking without warmup or synchronisation. CUDA is asynchronous; measure after a few warmup iterations and an explicit sync, or you're timing queue submission.
  • Assuming torch.compile is free. Measure it. On small models Python overhead was never the bottleneck, and compile time can exceed the savings.

Interview drill

Warm-up: Why does gradient checkpointing save memory, and what does it cost?

How a strong answer sounds
Normally every intermediate activation is kept from the forward pass until its backward runs, which is the dominant memory cost for deep models. Checkpointing stores only a few boundary activations and recomputes the rest during backward. Memory drops from roughly O(layers) to O(√layers) with the standard policy, at the cost of one extra forward pass — typically 20–35% more compute. It's the standard trade when you're memory-bound but have spare FLOPs, which is most large-model training.

Deeper: A profile shows 60% of step time in tiny elementwise kernels. What do you do?

How a strong answer sounds
Those kernels are memory-bound, so the goal is to move the tensor fewer times. First, enable compilation so the chain fuses into one kernel; check the log for graph breaks and remove the Python constructs causing them. Second, use fused implementations that already exist — fused optimizers, fused LayerNorm, FlashAttention. Third, check dtype: running elementwise chains in fp32 doubles the bytes. If it's still hot afterwards, write one Triton kernel for the specific chain. I'd re-profile after each change rather than applying all of them blind.

🧠 Key takeaways

  • The stack is Python → framework/autograd → compiler → kernels → hardware; performance problems live at a specific layer.
  • Tensors are memory plus metadata; views are free, and non-contiguity can silently trigger copies.
  • Reverse-mode autodiff saves activations for the whole forward pass — the main memory cost of training.
  • Compilation mainly wins by fusing memory-bound chains; graph breaks and reshape-driven recompiles undo it.
  • Profile first: gaps mean input starvation, tiny kernels mean fusion, big collectives mean communication overlap.

Check your understanding

What does x.T do to memory in a typical framework?

Transpose only changes metadata, so it's free — but the result is non-contiguous, and an op that requires contiguity will then copy.

Your validation loop OOMs while training runs fine at the same batch size. Most likely cause?

Without no_grad every op records itself and saves activations. Evaluation then costs as much memory as training — plus whatever training is already holding.

A profile shows regular gaps where no kernel is running. What is the most likely cause?

Periodic idle time between steps is the classic input-bound signature: add workers, prefetch, pin memory, or move preprocessing offline.

Why can torch.compile repeatedly recompile during training?

Compilers specialise on shapes. Variable-length batches produce a new graph each time — bucket the lengths or mark dimensions dynamic.

Why prefer safetensors over pickle-based checkpoints?

Loading a pickle runs code from the file — a real risk for downloaded weights. safetensors is a plain container: safer, and faster to load.

Inference & Serving Systems

Training is a project; serving is forever. An LLM serving stack is a scheduler around a memory-bound loop: keep the batch full, keep the KV cache packed, and hit a latency target you promised someone. Get this wrong and the model is fine while the product is unusable.

  • Separate prefill from decode and measure the right latency metrics
  • Explain continuous batching and why it beats static batching
  • Manage the KV cache with paging, preemption and prefix reuse
  • Plan capacity from QPS, token counts and a latency SLO
  • Design fallbacks, load shedding and autoscaling that behave under stress

Measure the right things

⏱️

TTFT

Time to first token. Dominated by queueing plus prefill. This is what “feels” fast.

⌨️

TPOT / ITL

Time per output token. Sets the reading speed; ~25 tokens/s is comfortably faster than reading.

📦

Throughput

Total tokens/second across all users. What your bill is proportional to.

👥

Concurrency

Requests in flight. Limited by KV-cache memory, not by compute.

⚖️
Throughput and latency pull in opposite directions

Bigger batches mean better GPU efficiency and higher total throughput — and a longer wait for any individual token. Every serving decision is a position on that curve, and the position should come from a stated SLO (“p95 TTFT < 1s, p95 TPOT < 50ms”), not from a default.

Batching: static, dynamic, continuous

Requests arrive at different times and finish after different numbers of tokens. Static batching — wait for N requests, run them together until all are done — wastes enormous capacity because the whole batch runs until the longest generation finishes.

Continuous batching, in one sentence

After every decoding step, evict finished sequences and admit waiting ones, so the batch is always as full as memory allows. It typically delivers 2–5× the throughput of static batching at the same latency, and it is the single most important feature of a modern inference server (vLLM, TensorRT-LLM, TGI, SGLang all do it).

The KV cache is the real constraint

Chapter 14 sized it: cache bytes grow with layers × width × context × concurrency. Two problems follow — fragmentation (reserving the maximum possible length per request wastes most of it) and eviction (what do you do when memory runs out mid-generation?).

Scheduling and fairness

With one shared GPU pool, a single 100k-token prompt can stall everyone else. Real schedulers manage that explicitly.

Prioritise by class

Interactive chat, background batch and internal evaluation should not compete equally. Separate queues with weights, or separate pools entirely, so a batch job can never push an interactive p95 over its SLO.

Bound the damage

Chunk long prefills, cap max output tokens per request, admit only what memory allows, and shed load with a clear 429 rather than accepting requests you'll time out on. A queue that grows without bound is an outage in slow motion.

🌀
Retries are dangerous here

A client timeout on a 30-second generation, retried three times, triples the load on a server that is already saturated — the classic retry storm. Use long, explicit client timeouts, cancel server-side work when the client disconnects (streaming makes this detectable), retry only on fast failures, and always with jitter and a circuit breaker.

🚀
Autoscale on queue depth, not utilization

GPU utilization is near 100% whenever anything is running, so it carries no signal about whether you have enough capacity. Scale on queue wait time or pending requests per replica, which is what actually maps to your latency SLO. And remember cold start: if a replica takes four minutes to load weights, your scaling signal must lead demand by at least that much — or keep a warm pool.

⚠️
Common mistakes
  • Benchmarking with batch size 1. It measures the worst possible efficiency and tells you nothing about production throughput.
  • Sizing GPUs by weights only. The KV cache decides concurrency; run out and throughput collapses regardless of FLOPs.
  • Reporting mean latency. Users experience p95 and p99, and the tail is where queueing lives.
  • No max-output-tokens cap. One runaway generation holds a slot for minutes.
  • Ignoring cancellation. Users close tabs constantly; without server-side cancellation you keep paying for abandoned work.
  • Putting variable content before the shared prefix. Destroys prefix caching — the cheapest latency and cost win available (Chapter 19).

Interview drill

Warm-up: Why does continuous batching help so much more for LLMs than for image classifiers?

How a strong answer sounds
Two reasons. First, generation lengths vary wildly, so in a static batch most slots sit idle waiting for the longest sequence — with image classification every item finishes in one pass. Second, decode is memory-bound: the weights are read from HBM for every step regardless of batch size, so adding sequences to the batch is nearly free in time and multiplies throughput. Continuous batching exploits both by refilling the batch after every single decoding step.

Deeper: p95 TTFT has degraded from 800 ms to 6 s with no traffic change. How do you diagnose it?

How a strong answer sounds
Split TTFT into queue time and prefill time — they have completely different causes. If queue time grew, the server is admission-limited: check KV-cache occupancy and preemption rate, since a few very long contexts can consume the memory that concurrency depends on; also check whether a batch workload started sharing the pool. If prefill time grew, look at input length distribution (a client started sending much larger prompts), prefix-cache hit rate (a prompt change invalidated it — a very common cause), and whether chunked prefill is enabled so long prompts don't block others. Then confirm with per-request logs of input tokens, cache hit, queue time and prefill time; that instrumentation is what makes this a five-minute investigation instead of a day.

🧠 Key takeaways

  • Prefill is compute-bound and decode is memory-bound; measure TTFT and TPOT separately.
  • Continuous batching refills the batch every decoding step and is the biggest throughput lever.
  • The KV cache limits concurrency; paging, prefix reuse, GQA and quantization all buy it back.
  • Plan capacity from token volume and an SLO, and autoscale on queue depth with warm pools.
  • Design for overload: shed load, cap outputs, cancel abandoned work, fall back to smaller models.

Check your understanding

Which metric best reflects “the assistant feels responsive”?

Users judge the wait before anything appears. After that, TPOT only needs to beat reading speed.

What primarily limits how many concurrent requests a GPU can serve?

Each in-flight sequence needs cache proportional to its context length. When that memory is exhausted, new requests queue no matter how idle the arithmetic units are.

What does paged attention primarily solve?

Fixed-size blocks allocated on demand — plus shareable blocks for identical prefixes — typically multiply usable concurrency several-fold.

Which autoscaling signal is most appropriate for an LLM serving pool?

GPU utilization saturates immediately and carries no headroom information. Queue depth maps directly to the latency SLO — and remember to lead demand by the replica cold-start time.

A client retries after a 10-second timeout while the server is overloaded. What's the risk?

The original work usually continues server-side, so retries add load without removing any. Long client timeouts, server-side cancellation, jittered backoff and a circuit breaker are the defences.

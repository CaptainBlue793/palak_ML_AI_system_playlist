Feature Stores & Training/Serving Skew

The most expensive bug in applied ML is not in the model. It's that the number called avg_order_value_30d in training is not the number with that name in production — computed by different code, from different data, at a different moment.

  • Name the three kinds of training/serving skew and how each arises
  • Build point-in-time-correct training sets with as-of joins
  • Describe feature store architecture and when it earns its cost
  • Choose between generating training data from logs or from the store
  • Monitor online/offline parity continuously

Three flavours of skew

🧮

Implementation skew

Training computes the feature in SQL; serving computes it in Python. Two implementations, two rounding rules, two null policies, and a drift that grows quietly.

⏰

Temporal skew

Training uses values as they are today; serving uses values as they were at request time. This is leakage, and it flatters your offline metrics.

📊

Distribution skew

Training data comes from a clean warehouse table; serving sees timeouts, nulls, defaults and a stale cache. The model has never seen the inputs it actually receives.

🔍
The signature

Excellent offline metrics, disappointing online results, and no obvious bug. Before blaming the model or the intervention, log the exact feature vector served for a sample of requests and compare it with the vector your training pipeline would have produced for the same entity at the same timestamp. Differences here explain more failed launches than every other cause combined.

Point-in-time correctness

A training row is (entity, timestamp, label). The features attached to it must be the values that were knowable at that timestamp — not the latest values, and not values from a table that has since been updated. That requires an as-of join, and it is fiddly enough that it's the main thing feature stores exist to do for you.

Also subtract the pipeline's own delay

Strictly, the correct question is not “what was true at time T?” but “what would the serving system have known at time T?”. If a feature pipeline lands data 20 minutes late, then at request time the online store held a value that was already 20 minutes old — so a training set built with instantaneous values is still optimistic. Good feature stores let you declare that delay and build training sets accordingly.

Two ways to build the training set

A · Reconstruct from history

Take labelled events and as-of join the offline store. Works retroactively for any model, lets you add features after the fact — and is exactly where point-in-time bugs live.

B · Log what you served

Write the exact feature vector used for each prediction, then join labels when they arrive. Zero skew by construction, and it's also your parity monitor. The catch: you can only train on features you were already serving, so new features still need path A.

✅
Do both

Log served feature vectors from day one — it costs a little storage and pays back the first time a launch underperforms. Use reconstruction to explore new features, and use the logs to verify that your reconstruction produces the same numbers. A weekly job that compares the two on a sample and alerts on divergence is one of the highest-value things in an ML platform.

Do you need a feature store?

SituationVerdict
One model, features computed from the request payloadNo. A shared function in your service is enough.
One model, batch predictions written to a tableNo. The warehouse is your feature store.
Several models sharing entity-level featuresProbably. The value is reuse and one definition, not the technology.
Real-time features with strict latency and point-in-time trainingYes. This is precisely the problem it solves.
Many teams, compliance requirements, feature lineageYes. The registry and governance become the main benefit.
🧰
The discipline matters more than the product

You can get 90% of the value with conventions: one repository of feature definitions, one execution path shared by training and serving, as-of joins in the training-set builder, served vectors logged, and a parity alert. Buying a feature store without those disciplines gives you a new system to operate and the same bugs.

⚠️
Common mistakes
  • Two implementations of one feature. They will diverge; the only question is when you notice.
  • Joining the latest feature values to historical labels. Leakage, great offline numbers, flat launch.
  • Ignoring the online store's staleness when building training data — the model learns from fresher data than it will ever see.
  • No default policy for timeouts. If a feature fetch fails at serving time, what value is used — and did the model ever see that value in training?
  • Unbounded feature sprawl. Hundreds of features, no owners, no TTLs, nobody able to delete anything safely.
  • No parity monitoring. Skew is silent by definition; it only shows up as a disappointing A/B result months later.

Interview drill

Warm-up: What is point-in-time correctness and why does it matter?

How a strong answer sounds
It means every feature attached to a training example reflects only what was knowable at that example's timestamp. Without it, a feature computed from data that arrived after the label leaks the future — the model appears to perform brilliantly offline and cannot reproduce it in production, because at inference that information doesn't exist yet. Implementing it means an as-of join on (entity, timestamp), and strictly it should also account for pipeline delay: what the serving system would have known, not what was true.

Deeper: Offline AUC 0.89, online lift zero. Design the investigation.

How a strong answer sounds
Assume skew until proven otherwise. Take a sample of production requests and log the exact served feature vector plus the model's output. Recompute the same features from the offline pipeline for the same entity and timestamp, and diff them feature by feature — large systematic differences point at implementation skew, small ones at staleness, and null spikes at timeout defaults. Separately, rebuild the training set with a strict as-of join including pipeline delay and see how much AUC survives; a big drop means temporal leakage. Then check distribution: compare the served values against the training distribution per feature, since serving sees defaults, retries and cold entities the warehouse never contained. Only after all three would I look at the model or at whether the intervention itself changes behaviour.

🧠 Key takeaways

  • Skew comes in implementation, temporal and distribution flavours; all three are silent.
  • Training rows need as-of joins that respect both event time and pipeline delay.
  • A feature store is a registry, an offline store, an online store and a materialization path — plus discipline.
  • Logging the served feature vector gives you zero-skew training data and a parity monitor for free.
  • You often don't need the product; you always need one definition and one execution path.

Check your understanding

You join today's customer_tier onto labels from 18 months ago. What kind of skew is this?

Values that only became true later are attached to earlier examples. The model learns a relationship that doesn't exist at prediction time.

What's the main advantage of logging the served feature vector?

You train on precisely what the model saw, including staleness, defaults and nulls. It doubles as your parity check — at the cost of only being able to train on features you already serve.

Your feature fetch times out for 2% of requests and the code substitutes 0. What must you check?

If the model never saw 0 in training, it interprets it as a real value — often a strong one. Represent missingness explicitly and include it in the training distribution.

When is a dedicated feature store least justified?

If there's nothing to share and no temporal join, a shared function in the service gives you the same guarantee without another system to run.

What should a parity monitor compare?

That comparison is the only direct measurement of skew. Alert on divergence per feature, because a single broken feature rarely moves an aggregate metric until it's too late.

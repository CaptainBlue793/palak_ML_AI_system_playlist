Case Study: Code Assistant

Inline completions for 500,000 developers, fired on almost every keystroke. The model must see enough of a million-line repository to be useful, answer before the developer has finished thinking, and be wrong quietly — because a suggestion that arrives late or reads badly is worse than no suggestion at all.

  • Design the keystroke-to-suggestion path under a 200 ms budget
  • Use fill-in-the-middle and repo context without blowing that budget
  • Cancel, debounce and cache aggressively — most requests should never reach a GPU
  • Measure acceptance and retention rather than token-level accuracy
  • Handle the security and licensing problems that come with generating code

In scope: inline completion, repo context, serving, caching, evaluation, safety. Out of scope: pretraining the code model (Chapter 16), the agentic multi-file editing mode, the IDE extension's UI.

🎯
Metrics

Primary: accepted characters retained — code the developer kept in the file some minutes later, not merely pressed Tab on. Secondary: acceptance rate, suggestion shown rate, weekly active users, share of characters typed by the assistant. Guardrails: p50 and p95 latency, cost per accepted completion, the rate of suggestions that fail to compile or lint, and the secret-leak rate. Deliberately not primary: next-token accuracy, which correlates weakly with anything a developer cares about.

⏱️
Latency is the product

A completion at 80 ms feels like the editor reading your mind. The same completion at 600 ms arrives after you have typed past it and reads as noise you have to dismiss. Internal experiments in this product category consistently show acceptance falling steeply as latency rises, well before users would call it "slow". That reframes every design choice: a smaller model that answers in 90 ms beats a better model that answers in 400 ms, and most of the engineering here is about not doing work rather than doing it faster.

2 · The completion path

One keystroke, end to endStep-through
  1. Fire after a short typing pause, not on every character, and cancel the in-flight request the moment the next keystroke lands. Without this you pay for three or four requests per accepted suggestion, and the cancelled ones still occupy GPU slots. The single highest-leverage optimisation here runs entirely on the client.
  2. The prefix (code before the cursor), the suffix (code after it), the file path and language, plus snippets from recently edited and open files and the symbols the current file imports. Assembled inside the IDE against a local index — a network round trip to fetch context would eat the entire budget.
  3. Hash the assembled prompt. Developers retype, undo, move the cursor back and re-trigger constantly, so an exact-match cache serves a surprising share of traffic in single-digit milliseconds. A close second: cache the model's KV prefix for the file so a second request on the same file skips most of the prefill.
  4. A small, quantized model — a few billion parameters — with a strict output cap: typically one line or one block, not a page. Speculative decoding with a tiny draft model roughly doubles throughput on code, which is unusually predictable text (Chapter 27).
  5. Trim at the first point where the suggestion starts repeating the suffix; stop at the end of the current block; check it parses; drop anything containing a credential-shaped string. A syntactically broken suggestion costs the developer more attention than an empty one.
  6. If the developer has typed since the request left, the result is thrown away and never shown. Ghost text appears only if it still matches what is on screen. Roughly one in four shown suggestions is accepted; the rest should cost the developer nothing to ignore.
  7. Shown, accepted, and — the number that matters — still present in the file some minutes later. Acceptance alone rewards suggestions that are easy to Tab through and immediately deleted (Chapter 33).

3 · Deep dive: fill-in-the-middle

A left-to-right model only sees what is above the cursor. Real editing happens in the middle of a file, where the code below the cursor is the strongest signal about what belongs. FIM training reorders documents so the model learns to condition on both sides.

<PRE>def parse_config(path: str) -> dict: with open(path) as f: raw = f.read() <SUF> return validated <MID>data = json.loads(raw) validated = ConfigSchema(**data).dict()

The training document is rearranged into prefix, then suffix, then middle, so at inference the model is asked to continue after <MID> with both sides already in context. The same model still serves plain left-to-right completion when there is no suffix — one model, two shapes of request.

🧩
Repo context: retrieval with a millisecond budget

Embedding-based retrieval over the repository is the obvious idea and usually the wrong one here: even 40 ms of vector search is a third of the budget, and it happens on every keystroke. What works is cheaper and mostly lexical, computed continuously in the background by the IDE:

Recently edited files (the strongest single signal — you are usually working on related code), open tabs, the symbols this file imports resolved to their definitions, sibling files in the same directory, and identifier overlap with the current function. Rank these by a simple score, take a few hundred tokens each, and stop. The heavier retrieval belongs in chat and agent modes, where a 400 ms retrieval is invisible next to a multi-second answer.

Ship through online experiments with retained characters as the primary metric and latency as a guardrail (Chapter 33). Offline suites gate releases; only live traffic settles whether a change helped.

🔑
Three failure modes that are not about quality

Secrets. Models trained on public code will occasionally emit credential-shaped strings, and developers do paste keys into files. Scan every suggestion with the same detectors you run in CI, and never log raw prompts without redaction — the prompt is the customer's source code.

Licensing. Long verbatim reproductions of distinctive training code create a legal exposure that no accuracy metric shows. A near-duplicate check against known corpora, plus an option to suppress long exact matches, is the standard mitigation.

Injection through the repository. In agent and chat modes the model reads files, and a comment in a file can be written by anyone who can open a pull request. Treat repository content as data, and require confirmation before the assistant runs a command or edits outside the file in view (Chapter 36).

🎤
Interview drill

Follow-up: “You have a model with clearly better offline scores but 250 ms more latency. Ship it?”

How a strong answer sounds
Not for inline completion, and I would want the experiment to prove it rather than arguing from principle. Acceptance is strongly latency-sensitive in this product shape, so a model that is better per suggestion but arrives after the developer has typed past it will usually lose on retained characters — the offline win never reaches the user. What I would do instead: run it as a shadow to confirm the quality gap is real on our traffic, then try to buy the latency back — quantization, speculative decoding, a tighter output cap, better prefix caching. If it still cannot fit the budget, route it to the modes where the budget is different: chat, multi-line block completion on an explicit trigger, and the agent path, where 400 ms is invisible. Two models serving two latency regimes is a perfectly good answer, and it is usually the right one.

Follow-up: “Acceptance rate went up 3% after a change. Is that good?”

How a strong answer sounds
It is a hypothesis, not a result. Acceptance is gameable in ways that hurt users: shortening suggestions raises it, suggesting only in trivially predictable positions raises it, and a developer who accepts then immediately deletes still counts. I would check retained characters — is the accepted code still there minutes later? — and the shown rate, because acceptance is a ratio and it moves if the denominator changes. Then slice by language, by file size and by whether the suggestion was single or multi-line, since an aggregate win often hides a regression in the languages a minority of developers use all day. If retained characters moved with acceptance and latency held, I would believe it and ship.

🧠 Key takeaways

  • Latency is the dominant quality lever for inline completion; a smaller fast model usually beats a better slow one.
  • Most of the win comes from not doing work — debouncing, cancelling and caching remove roughly two-thirds of requests before a GPU sees them.
  • Fill-in-the-middle exists because real editing happens mid-file, and the code below the cursor is a strong signal.
  • Repo context must be assembled locally from cheap signals; embedding search is too slow for the keystroke path.
  • Measure retained characters, not acceptance and certainly not token accuracy — and treat secret leakage and licensing as first-class failure modes.

Check your understanding

Why does inline completion use fill-in-the-middle rather than plain left-to-right generation?

FIM reorders training documents into prefix, suffix, middle so the model can condition on both sides — which is what a developer's cursor position actually looks like.

Which change most reduces GPU cost per accepted completion?

Requests that never reach a GPU are free. Without cancellation propagating to the scheduler, superseded requests keep decoding and you pay for suggestions nobody will ever see.

Why is acceptance rate a poor primary metric?

Retained characters (still in the file minutes later) is the better proxy: it penalises suggestions that are easy to accept and immediately deleted.

Why is prefill, rather than decode, the dominant serving cost here?

The inverse of a chat product. That makes prefix caching and context-size discipline the highest-value optimisations, not decode throughput.

Why must every suggestion be scanned before it is displayed?

Secret emission and verbatim reproduction are failure modes no accuracy metric surfaces, and both are far cheaper to stop before display than to clean up afterwards.

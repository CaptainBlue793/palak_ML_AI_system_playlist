Vector Search & ANN Indexes

Retrieval is the backbone of RAG, recommendation, deduplication and semantic search. The core operation — find the nearest vectors to this one — is trivially simple and computationally brutal at scale, so everything interesting is in the approximations.

  • Explain why exact nearest-neighbour search doesn't scale
  • Compare flat, IVF, HNSW and product-quantized indexes
  • Tune recall against latency and memory deliberately
  • Handle metadata filters, updates and multi-tenancy
  • Combine lexical and vector retrieval into hybrid search

The problem

Exact search compares the query to every vector: 50M vectors × 768 dimensions is ~38 billion multiply-adds per query. On one core that's seconds; you need single-digit milliseconds, at thousands of queries per second. Approximate nearest neighbour search trades a little recall for two to three orders of magnitude of speed.

🎯
Approximate is fine — but measure it

Recall@10 of 0.95 means you found 9.5 of the true top 10 on average. For RAG that's usually invisible, because a re-ranker and the LLM both tolerate a missing marginal result. For deduplication or compliance search it may not be. Decide the recall target from the application, then tune to hit it — never accept a library's defaults blind.

How HNSW actually searches

Vectors become nodes in a graph where each node links to its near neighbours. Search is greedy: start somewhere, hop to whichever neighbour is closer to the query, repeat until no neighbour improves. Multiple layers (sparse at the top, dense at the bottom) turn this into a coarse-to-fine descent — a skip list in metric space.

Raising ef_search keeps more candidates alive, exploring more of the graph: higher recall, more distance computations, more latency. It is a query-time knob, so you can tune it per request — cheap for autocomplete, thorough for compliance search.

The three-way trade-off

Recall, latency and memory. You can have two comfortably; the third is what you're paying for.

💾
Memory is the real cost driver

A graph index must be in RAM to be fast, and RAM is the expensive part of the bill. 100M × 768-dim float32 vectors is ~307 GB before the graph's ~60% overhead. Scalar quantization to int8 cuts that 4× for around a point of recall; product quantization cuts it 10–50× and needs a rerank pass. Design the memory budget first, then pick the index that fits it.

Filters, updates and tenancy

🔎

Filtered search

Post-filter (search then drop) breaks when the filter is selective — you retrieve 100 and keep 2. Pre-filter (restrict then search) is exact but can defeat the index. Good engines do filtered traversal: apply the predicate during graph search.

♻️

Updates & deletes

Graph indexes don't remove nodes cleanly — deletes are usually tombstones, and quality degrades until a rebuild. Plan a periodic compaction, and treat “rebuild the index” as a routine operation with a shadow-index swap.

🏢

Multi-tenancy

Per-tenant indexes isolate perfectly but waste memory on small tenants. A shared index with a tenant filter is efficient but makes isolation a correctness and security property — test it explicitly (Chapters 37, 46).

🔐
Permissions are part of retrieval, not a post-processing step

If a user may not see a document, it must not be retrievable — not filtered out afterwards, and certainly not summarised into an answer before filtering. Store ACLs alongside vectors and push them into the search as a filter; verify with a test that retrieves as user A and asserts nothing from user B appears. This is one of the few genuine security boundaries in a RAG system.

Hybrid search: lexical plus vector

Embeddings are excellent at meaning and unreliable at exact strings: product codes, error numbers, names, rare acronyms. BM25 is the opposite. Running both and fusing the results beats either alone on almost every real corpus.

Choosing the storage

Start with what you have

Under ~1M vectors with modest QPS, pgvector (or your existing search engine's vector support) is usually enough — and it gives you transactions, joins, filters and backups for free. Adding a dedicated vector database is a real operational commitment.

Move when you hit a wall

Dedicated engines (Qdrant, Milvus, Vespa, Weaviate, managed services) earn their place at tens of millions of vectors, high QPS, heavy filtering or hybrid ranking. Migrate for a measured reason — index build time, p99 latency, memory cost — not for the category.

⚠️
Common mistakes
  • Never measuring recall. Sample 1,000 queries, compute exact top-k offline, and track recall@k as a monitored metric.
  • Mixing normalized and unnormalized vectors, or cosine and L2 between index and query. Silent, severe quality loss.
  • Post-filtering a selective predicate. Retrieve 100, filter to 3, wonder why results are poor — push the filter into the search.
  • Forgetting the index is stale. Deletes leave tombstones; new documents need indexing latency budgets and a rebuild cadence.
  • Vector-only retrieval. Exact identifiers, codes and names need lexical matching — hybrid is the default for a reason.
  • Changing the embedding model without reindexing. Chapter 15's warning, and it stays the top cause of overnight quality collapse.

Interview drill

Warm-up: When would you pick IVF-PQ over HNSW?

How a strong answer sounds
When memory is the binding constraint. HNSW gives the best recall-per-millisecond but stores full vectors plus a graph, so it's roughly 1.6× the raw vector size in RAM. IVF-PQ compresses vectors into short codes — often 10–50× smaller — so a billion vectors fit on a single machine, at the cost of lossy distances that need a rerank against exact vectors for the top candidates. So: HNSW for tens of millions where latency matters most; IVF-PQ or DiskANN when the corpus is enormous or the RAM budget is fixed.

Deeper: Design retrieval for 500M chunks with per-user permissions and a 50 ms p99.

How a strong answer sounds
Shard by document collection or tenant so each shard is a few tens of millions of vectors, with replicas for QPS and availability; fan out and merge. Per shard, use a compressed index (IVF-PQ or int8-quantized HNSW) sized to fit in RAM, and rerank the top ~200 against exact vectors. Permissions go into the index as filters applied during traversal, not afterwards, with ACL changes propagated on a short lag and a documented worst-case staleness. Add a lexical index for exact-identifier queries and fuse with RRF. For latency: cap ef_search per request, keep the fan-out bounded, cache hot queries, and measure recall@k continuously against an offline exact ground truth so I know what the speed is costing me.

🧠 Key takeaways

  • ANN trades a measurable amount of recall for orders of magnitude in speed — pick the recall target from the application.
  • HNSW is the default for quality and latency; IVF-PQ and disk-based indexes win when memory is the constraint.
  • ef_search / nprobe is a per-query knob: tune effort by request type.
  • Push filters and permissions into the search itself, and plan for deletes and rebuilds.
  • Hybrid lexical + vector retrieval with rank fusion beats either alone on real corpora.

Check your understanding

What does ef_search control in HNSW?

Neighbours per node is M, set at build time. ef_search is a query-time parameter you can vary per request.

Your filter matches 0.1% of documents and results are poor. Most likely cause?

With a highly selective predicate, post-filtering leaves a handful of results from an unrelated neighbourhood. Apply the filter during traversal, or maintain a separate index for that partition.

Which query is vector search most likely to handle worse than BM25?

Identifiers carry no semantics and tokenize into fragments. Exact lexical matching is what finds them — hence hybrid retrieval.

You have 800M vectors at 1024 dims and a fixed RAM budget. What's the most appropriate approach?

Raw float32 alone would be ~3.3 TB. Compression makes the corpus fit; reranking the top candidates against exact vectors restores most of the lost precision.

What does Reciprocal Rank Fusion solve?

BM25 scores and cosine similarities aren't comparable. RRF uses only ranks, so the two systems can be fused robustly with one parameter.

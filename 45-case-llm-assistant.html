Case Study: LLM Chat Assistant

Serve a conversational assistant to 10 million daily users: streaming responses, multi-turn context that grows every message, tool use, safety filtering, several model tiers, and a cost per conversation that has to stay below what the product earns.

  • Design the request path from gateway to token stream
  • Control the cost of growing conversation context
  • Exploit prefix caching and routing to cut spend several-fold
  • Build the safety pipeline without destroying usefulness
  • Measure quality continuously in production

2 · The request path

One message, end to endStep-through
  1. Server-sent events over a long-lived HTTP connection. The client sends the new message plus a conversation id — not the whole history, which the server already has. Disconnection must be detectable so the server can cancel and free the slot (Chapter 26).
  2. Authenticate, resolve tenant and plan, check rate limit and token quota, choose the model tier, attach a trace id. Thin and fast — this is on the path of every message in the product (Chapter 39).
  3. Stable system prompt and tool schemas first (for caching), then long-term memory, then retrieved documents if the query needs them, then the conversation history, then the new message. Order is chosen for prefix caching, not for readability.
  4. A fast classifier on the user message; retrieved content fenced as untrusted data. Runs in parallel with cache warming so it costs almost no wall-clock time (Chapter 36).
  5. The scheduler finds the cached KV prefix for this conversation, prefills only the new tokens, and joins the continuous batch. This is the difference between prefilling 400 tokens and 40,000 on turn twenty.
  6. The model emits a structured call; the gateway authorises it against the user's permissions, executes in a sandbox with a timeout, and feeds the result back as untrusted data. The conversation continues in the same stream (Chapter 22).
  7. Tokens stream to the client as they're produced, through an output filter that buffers a small window so a policy violation can be stopped mid-stream rather than after the user has read it.
  8. First token typically within 600 ms. Everything — prompt version, model version, cache hit, token counts, latency, tool calls, user feedback — is traced. A sample goes to automated grading and weekly human review (Chapter 35).

Conversation-aware routing is what makes prefix caching work

A cached KV prefix lives on one specific replica. If the next turn lands elsewhere, the cache misses and you prefill 40,000 tokens again. So the router uses sticky, conversation-affine routing — hash the conversation id to a replica, with a fallback when that replica is overloaded or dies. Cache hit rate becomes a first-class serving metric: a drop from 85% to 40% roughly doubles prefill cost and visibly raises TTFT, and it's usually caused by a deployment or a routing change rather than by anything about the model.

5 · Deep dive: safety without ruining the product

InputFast classifier on the user message; separate handling for retrieved and tool content, which is fenced as data. Latency budget: under 30 ms, run concurrently with cache warming.
SystemPolicy in the system prompt sets defaults, not guarantees. It is the cheapest layer and the weakest one (Chapter 36).
OutputStreaming filter with a small look-ahead buffer, so a violation is caught before the user reads it. Must not add perceptible delay to the first token.
ActionAnything with a side effect — sending, purchasing, deleting — is authorised in code against the user's real permissions, never by the model's say-so.
FeedbackRed-team suite in CI, sampled human review of refusals and near-misses, and a measured false-refusal rate so safety work doesn't quietly make the product useless.
🙅
Over-refusal is a product failure with no error code

Every safety change should be evaluated on two sets: the harmful set (does it block?) and a benign near-miss set — security questions, medical questions, fiction, anything that pattern-matches to something risky. Teams that only measure the first ship assistants that refuse to explain how to kill a Linux process. Track false-refusal rate as a guardrail with the same seriousness as the violation rate.

🔀
Disaggregating prefill from decode

Prefill is compute-bound and bursty; decode is memory-bound and steady. Running them on the same replicas means a single 100k-token prompt stalls everyone else's token stream. Splitting them — prefill on one pool, decode on another, with the KV cache transferred between them — lets each pool be sized, batched and scaled for its own profile. The cost is a network transfer of the cache, which is worth it above a certain scale and is over-engineering below it.

Interview drill

Follow-up: “Cost per conversation doubled last week with flat traffic.” Where do you look?

How a strong answer sounds
Cost per conversation is tokens × price, so I'd decompose it. Input tokens per message: did a prompt change, a memory feature, or a retrieval change add context? Prefix cache hit rate: a system-prompt edit or a routing change invalidates every cached prefix and silently doubles prefill — this is the single most common cause. Output length: a model or prompt change can make answers longer. Routing mix: are requests that used to go to the small tier now escalating? Conversation length: did a product change make sessions longer? All five are visible in the traces if the gateway logs token counts, cache hits and the routing decision per request — which is exactly why it should.

Follow-up: “How do you know quality hasn't regressed?”

How a strong answer sounds
Offline gates before release: a golden set of real conversations graded pairwise against the current production configuration, plus capability slices and a safety suite (Chapter 35). In production, continuously: sample a fraction of live conversations for automated rubric grading, with weekly human review of a smaller sample calibrated against the judge; watch implicit signals — regeneration rate, thumbs-down, conversation abandonment, escalation to support — sliced by model tier and route. Then any change ships through shadow and canary with those as guardrails. The offline number decides whether we try it; the production signals decide whether it stays.

🧠 Key takeaways

  • Conversation cost grows quadratically with turns unless you cache prefixes and manage history.
  • Prefix caching only works with conversation-affine routing — track cache hit rate as a serving metric.
  • Tiered routing plus caching is the difference between viable and unviable unit economics.
  • Safety is layered, and false-refusal rate is a guardrail as important as violation rate.
  • Quality needs continuous sampled grading in production; infrastructure metrics cannot see it.

Check your understanding

Why does a chat conversation's cost grow faster than linearly with turns?

Turn n prefills roughly n turns of history. Summed over a conversation that's O(n²) — which is why prefix caching is the single most valuable optimisation here.

Why must routing be conversation-affine?

Cache locality is the whole point. Sticky routing with an overload fallback preserves hit rate; round-robin destroys it.

Why separate prefill and decode onto different pools at large scale?

Prefill is compute-bound and bursty, decode is memory-bound and steady. Splitting lets each be sized and batched appropriately, at the cost of transferring the KV cache.

Your safety change reduced violations by 40%. What else must you measure before shipping?

Blocking more is trivially easy. The cost shows up as refusing legitimate requests, which has no error code and drives users away silently.

TTFT rose from 600 ms to 2.4 s with unchanged traffic and no errors. First hypothesis?

A cache miss means prefilling the whole conversation again. It shows up as a latency and cost change with every system metric looking healthy — which is why hit rate needs its own alert.

Case Study: Image Generation Service

Text-to-image for three million users. Every request occupies a whole GPU for seconds at a time, so this is the one system in the course where a single user's request can meaningfully degrade everyone else's. Capacity, queueing and abuse control matter more here than model quality — and the safety problem has no equivalent in a text product.

  • Design an asynchronous request path around multi-second GPU work
  • Trade denoising steps against quality, latency and cost
  • Queue fairly when one user can consume a GPU for a minute
  • Build a safety pipeline covering prompts, outputs and provenance
  • Store and serve images without the storage bill overtaking the GPU bill

🎯
Metrics

Primary: images kept — downloaded, shared or saved to a project — per active user per week. Generation counts reward people regenerating because the first result was poor. Quality: human preference on a fixed prompt suite, prompt-adherence scores, regeneration rate as an implicit signal. Guardrails: p50 and p95 time to first image, queue wait at peak, GPU seconds per kept image, policy-violation rate, false-block rate. Cost line: GPU seconds per image is the unit that everything else converts into.

🧮
Why this system is not like the others

A chat token takes milliseconds and shares a GPU with fifty other conversations. A 1024² image at 30 steps occupies a substantial slice of a GPU for several seconds and cannot be interleaved nearly as finely. The consequences run through every design decision: requests must be asynchronous with a job id rather than a held-open connection; queue depth, not utilization, is the health metric; admission control has to exist on day one; and a single abusive client can consume the capacity of thousands of ordinary users without tripping any rate limit expressed in requests per second.

2 · The request path

Prompt to delivered imageStep-through
  1. The API returns immediately with a job id and a queue position; the client subscribes for progress. Holding an HTTP connection open for eight seconds of GPU work wastes a connection slot, breaks through proxies, and makes retries indistinguishable from new work — so the job, not the connection, is the unit of state.
  2. Classify the prompt, match against blocklists for named real people and known abuse patterns, and reject or rewrite. This runs first for a practical reason as well as a policy one: rejecting in 20 ms costs nothing, whereas generating and then discarding an image costs eight GPU seconds you can never sell.
  3. Jobs enter priority classes — interactive paid, free tier, batch and API — each with a GPU-second budget rather than a request-per-second limit. The scheduler picks by class weight and per-user fair share, so one user submitting 500 jobs delays their own queue, not everyone else's.
  4. The actual work: encode the prompt, then run N denoising steps over the latent, then decode to pixels. Batching a few jobs with identical parameters improves throughput; batching jobs with different step counts or resolutions does not, so the scheduler groups compatible work.
  5. Decode a low-resolution preview from the latent after a handful of steps and stream it. Perceived latency drops enormously — the user sees the composition forming at 1.2 s instead of a spinner until 6 s — for a few percent of extra compute.
  6. An image classifier on the result, perceptual-hash matching against known-illegal content, and an embedded provenance signal plus signed metadata. Some violations are only detectable in the output: the prompt was innocuous and the model produced something that is not.
  7. Write to object storage with a lifecycle policy, serve through a CDN behind short-lived signed URLs. Record seed, model version and every parameter — regeneration, "make a variation of this", billing disputes and abuse investigations all depend on that record (Chapter 31).
  8. The client already has the preview; the final image replaces it. Failed jobs must be visibly failed and not silently charged — a job that dies mid-denoise has consumed real GPU seconds, and deciding who pays for those is a product decision you should make before launch.

🧭
Tiering by step count is the practical answer

You do not have to pick one. Use a 4-step distilled model for previews, thumbnails, variations and free-tier traffic — where speed matters more than the last few percent of fidelity — and a higher-step configuration for final renders, upscales and paid requests. The model weights differ but the pipeline does not, so the scheduler simply routes by tier. The mistake is picking the high-quality configuration for everything and then discovering the fleet costs four times what the product earns.

Cold starts are the other scheduling trap: loading a multi-gigabyte diffusion model takes tens of seconds, so scaling up after the queue builds is far too late. Keep a warm pool sized to the daily peak, and pre-warm on the schedule your traffic actually follows.

5 · Deep dive: safety and abuse

PromptClassifier plus blocklists for named real individuals, sexual content involving minors, and known circumvention phrasings. Cheap, fast, and the only gate that saves GPU time. Also the easiest to evade, which is why it cannot be the only one.
Image inputImage-to-image and inpainting change the threat model completely: the uploaded photo is the payload. Run face detection and consent policy on uploads, not just on prompts, and treat "edit this photo of a real person" as a distinct product decision.
OutputA classifier on the generated pixels catches what the prompt did not reveal, and perceptual hashing matches known-illegal material. Some violations only exist in the output — the prompt was benign and the model was not.
ProvenanceEmbedded watermark plus signed content credentials in the metadata. Metadata gets stripped by every re-upload, so the watermark is what survives; neither is proof, both are evidence.
AccountsAbuse is concentrated: a small number of accounts generate most violations. Per-account violation tracking, graduated enforcement and a genuine appeals path catch far more than any per-request classifier.
MeasurementTrack the violation rate and the false-block rate. A filter tuned only against violations ends up refusing "a woman in a swimming pool" and the product dies of a thousand irritations (Chapter 37).

🎤
Interview drill

Follow-up: “At peak, p95 wait hits 40 seconds. You cannot get more GPUs this quarter. What do you do?”

How a strong answer sounds
I would attack demand and work per job before touching quality for everyone. First, find out where the GPU seconds are going: I would expect a small fraction of users, and the batch and API classes, to account for most of it, so enforcing GPU-second fair share redistributes wait rather than adding capacity — the median user's experience improves immediately. Second, shift default step counts down at peak only, using the distilled model for previews and free-tier requests, with the high-step path reserved for explicit final renders; that is a several-fold throughput gain for a quality difference most users will not see on a first draft. Third, deduplicate: identical prompt, seed and parameters should return the cached image rather than regenerating it. Fourth, move batch and API work to off-peak with a deadline-based scheduler, since those jobs have hours of slack and interactive jobs have seconds. And I would make the wait honest — showing a real estimate and a lower-quality instant option beats a spinner, because retries during a queue backup are what turn a slow system into a broken one.

Follow-up: “Why not rate-limit by requests per minute like a normal API?”

How a strong answer sounds
Because requests are not the resource. One request can be a 512² four-step preview costing half a GPU second, or four 2048² images at 50 steps costing well over a minute — a difference of two orders of magnitude priced identically. A request limit therefore either throttles the cheap users unnecessarily or leaves the expensive path wide open, and in practice it does both. The correct unit is GPU seconds: budget them per account and per priority class, charge jobs against the budget as they run, and let the scheduler enforce fair share. It also gives you a cost model that matches the bill, so quotas, pricing and capacity planning are all denominated in the same thing.

🧠 Key takeaways

  • Multi-second GPU jobs force an asynchronous design: a job id, progress streaming, and queue depth as the health metric.
  • The step count sets quality, latency and fleet size at once; distilled few-step models plus tiering are how the economics work.
  • Limit and schedule by GPU seconds, not requests — a single request can vary a hundred-fold in cost.
  • Safety needs gates on the prompt, on uploaded images and on the output, plus account-level enforcement and a measured false-block rate.
  • Recording seed and parameters makes images reproducible, which turns storage into a cache — as long as the model version survives.

Check your understanding

Why should quotas be denominated in GPU seconds rather than requests per minute?

A 512² four-step preview and four 2048² 50-step images are both "one request". Pricing them the same either over-throttles cheap traffic or leaves the expensive path open.

Why is GPU utilization a poor health signal for this service?

The scheduler keeps GPUs busy whether the queue is empty or forty seconds deep. Autoscale and alert on queue depth in GPU seconds, which leads demand instead of lagging it.

Why run the prompt safety classifier before scheduling rather than after generation?

It is a capacity decision as much as a policy one. The output classifier is still needed, because a benign prompt can produce a violating image.

What makes streaming a low-resolution preview so valuable?

The user sees composition forming in about a second instead of a spinner until the final image. Nothing about the final result changes; the experience changes completely.

Why record the seed and all sampler parameters for every job?

Regenerating from a seed can be cheaper than keeping a rarely-viewed image in cold storage — but only while the pinned model version still exists, which constrains how fast you retire versions.

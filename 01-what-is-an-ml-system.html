What Is an ML System?

Before any maths, let's get the shape of the thing. A machine learning system is not a model — it is a pipeline of data, training, evaluation, serving and monitoring, wrapped around a model that is usually the smallest part of it.

Rules, or learning?

Ordinary software is rules you write: if the cart total is over £50, shipping is free. Machine learning is rules the machine infers from examples: here are 200,000 emails labelled spam or not spam — work out the rule yourself.

That flip is only worth it when the rule is too complicated, too fuzzy, or too fast-moving for a person to write down. Try it below: add hand-written rules to a spam filter and watch how quickly they stop generalising.

The honest test for “should this be ML?”

Use ML when (1) the pattern exists but nobody can write it down, (2) you have (or can get) labelled examples of it, (3) the pattern changes, so hand-written rules would rot, and (4) a wrong answer now and then is survivable. Miss any of those and rules are cheaper, faster and far easier to debug.

The three ingredients

Every supervised ML system — from a 10-line logistic regression to a trillion-parameter language model — is built from exactly three things.

🧱

Data

Examples of the thing you want to predict, with the answer attached (labels). Almost all of your effort will live here.

🧠

Model

A function with adjustable numbers (parameters) flexible enough to represent the pattern you're after.

🎯

Objective

A loss function that scores how wrong a prediction is, plus an optimizer that nudges the parameters to reduce it.

🎸
Analogy: learning guitar by ear

The data is the recording you're copying. The model is your hands and their thousands of possible positions. The loss is how wrong the note sounds. Practice is gradient descent: play, hear the error, move your fingers slightly in the direction that sounds better. Nobody hands you the rule “index finger on fret 3” — you infer it from feedback, which is exactly what training is.

The lifecycle: where the work actually goes

People picture ML as “train a model”. In production it's a loop that never stops turning, and the model step is one box out of eight. Step through it:

The ML lifecycleStep-through
  1. Turn a business goal into a prediction task and a metric. “Reduce churn” becomes “predict P(user cancels in next 30 days)”, measured by PR-AUC offline and retained revenue online. Getting this wrong makes every later step worthless.
  2. Find or build a dataset with labels, decide how far back it is trustworthy, and split it into train/validation/test before you look at it. Chapter 3 is entirely about the ways this goes wrong.
  3. Turn raw rows, text, images or events into numbers a model can consume: encode categories, scale, aggregate over windows, embed. For deep models the network learns most of this — but not the part that reads from your production systems.
  4. Fit parameters by minimising a loss, then tune the knobs you chose yourself (learning rate, depth, regularization). A first model should take hours, not weeks — you want a baseline to beat.
  5. Score it on held-out data with a metric that matches the decision the model drives, plus slices (new users, each country, each device). An average that hides a broken segment is how models ship broken.
  6. Ship behind a flag: shadow traffic first, then a small canary, then a real A/B test. The offline metric only predicts the online one — Chapter 33 is about the gap between them.
  7. Answer live requests inside a latency budget, at a cost per prediction you can afford, with a fallback for when the model is unavailable. This is a systems problem, and it's most of Level 3.
  8. Watch inputs for drift, outputs for quality, and the world for the labels that eventually arrive. When behaviour shifts — and it will — you collect new data and go round again. An ML system is never “done”.

The feedback loop, concretely

A feed model ranks cat videos slightly higher. Users watch more cat videos. The next training set is full of cat-video watches. The model ranks them higher still. Three months later the product is a cat-video app and nobody decided that. Every recommender has this problem; Chapter 30 covers how to keep exploring.

Offline metrics vs. the thing you care about

Models are trained on a proxy. The product is measured on something else. Keeping those two connected — and being honest about the gap — is the core skill of an ML engineer.

📏 Model metric

AUC, F1, perplexity, BLEU, recall@10. Computable offline, in seconds, on a fixed dataset. Useful for iteration, and a lie if you optimise it far enough.

💷 Product metric

Retention, revenue, fraud losses, tickets deflected, time saved. Measured online over days or weeks with an experiment. The thing you actually promised — and always noisier than you want.

🎤
Interview tip

When asked to design an ML system, state both metrics in the first two minutes: “offline I'll track PR-AUC on held-out fraud; online the decision metric is chargeback loss per £1,000 processed, guard-railed on false-decline rate.” That single sentence separates people who have shipped models from people who have only trained them.

A framework for any ML design problem

Every case study in this course follows this sequence, and so should you in an interview or a design doc.

1. Clarify the task and the metric ~5 min

What decision does the prediction drive? Who acts on it? Offline metric, online metric, and the constraint that must not regress.

2. Data and labels ~7 min

Where do examples come from, how are labels produced, how delayed are they, how much do you have, and what is the split strategy?

3. Features and representation ~5 min

What signal exists at prediction time — and only at prediction time? Categorical, sequential, text, embeddings.

4. Model choice and baseline ~5 min

Start with the simplest thing that could work (a heuristic, then GBDT, then deep). Say explicitly what you're comparing against.

5. Training and evaluation plan ~8 min

Compute budget, retraining cadence, validation design, slice metrics, and how you'll catch leakage.

6. Serving design ~10 min

Online vs batch, latency budget, hardware, caching, fallbacks, and the shape of the request path.

7. Monitoring, rollout and iteration ~7 min

Shadow → canary → A/B, drift alarms, feedback collection, and the retraining loop that keeps it alive.

⚠️
Common mistakes
  • Reaching for ML when three rules would do. A learned model costs a pipeline, a training job, a serving stack and a monitoring story, forever. If a threshold solves 90% of it, ship the threshold and collect data.
  • Optimising a metric nobody asked for. Accuracy on a 99%-negative dataset is 99% for a model that says “no” to everything. Pick the metric from the decision, not from the tutorial.
  • Treating deployment as the finish line. The day a model ships is the day its data starts drifting. Budget for monitoring and retraining in the original plan, not as a follow-up ticket.
  • Ignoring the no-model baseline. “Most popular item”, “yesterday's value”, “the rule the ops team already uses” — if you can't beat those, you have learned something valuable and cheap.
🎤
Interview drill

Warm-up: A product manager says “let's add AI to the checkout page.” What do you ask before agreeing?

How a strong answer sounds
What decision should change, and what metric would move if it worked? Do we have logged examples of that decision with outcomes, and how delayed are the outcomes? What is the cost of a wrong prediction in each direction? What latency budget does checkout allow? And what is the simplest non-ML baseline — because if a rule gets most of the value, ML is a second-phase investment, not the first one.

Explain it simply: Why is an ML system harder to maintain than a normal service with the same traffic?

How a strong answer sounds
Because its behaviour depends on data, and data changes without anyone deploying. Ordinary services fail loudly and deterministically; ML systems degrade silently as the world drifts away from the training distribution, and the failure often shows up first in a business metric rather than an error rate. That means the maintenance surface includes pipelines, feature parity between training and serving, label collection, drift monitoring and a retraining path — none of which exist for a CRUD service.

🧠 Key takeaways

  • Use ML when the pattern exists, is hard to write down, changes over time, and occasional errors are tolerable.
  • Every ML system is data + model + objective; the data is where the effort and the failures live.
  • The lifecycle is a loop — frame, data, features, train, evaluate, deploy, serve, monitor — not a straight line.
  • Model code is a sliver of a production ML system; the rest is data and systems engineering.
  • Always name an offline metric and the product metric it is a proxy for, plus the baseline you must beat.

Check your understanding

Which problem is the worst fit for machine learning?

VAT is a known, exact, legally specified rule. Learning it from examples would be slower, more expensive and occasionally wrong — for a rule you can write in one line.

“Predict the next token in this text” is an example of which kind of learning?

The label (the next token) comes free from the raw data itself — no annotator needed. That is what makes internet-scale pretraining possible.

Your churn model scores 0.91 AUC offline but the A/B test shows no change in retention. What is the most likely explanation?

A perfect predictor of who will leave is useless if the discount you send them doesn't change their mind. The offline metric measures prediction; the product metric measures the decision the prediction drives.

Which of these is a uniquely “ML” failure mode rather than an ordinary software bug?

Nothing errors, all requests return 200, and the only symptom is a slow-moving quality metric. That silent-degradation shape is why ML systems need data and quality monitoring, not just uptime monitoring.

In an ML design interview, what should come first?

Every later decision — model, features, hardware — depends on what you are predicting, how success is measured and what you must beat. Starting with the model is guessing.

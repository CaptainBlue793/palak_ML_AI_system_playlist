Distributed Training I: Data Parallel, ZeRO & FSDP

Two reasons to use more than one GPU: the model doesn't fit, or it would take too long. Data parallelism solves the second. ZeRO and FSDP extend it to solve the first — by noticing that every GPU is holding an identical copy of things only one of them needs at a time.

Data parallelism in one picture

Every GPU holds a full copy of the model. The global batch is split between them; each computes gradients on its shard; then all gradients are averaged so every replica applies an identical update and the copies stay in sync.

One data-parallel stepStep-through
  1. Each GPU takes a different slice. With 4 GPUs and a 4M-token global batch, each processes 1M tokens. The per-device batch is what has to fit in memory; the global batch is what determines the learning-rate schedule.
  2. Every replica runs the same computation on different data. No communication at all — this phase scales perfectly.
  3. Each GPU computes gradients for every parameter, but only from its own data. Four different gradient vectors now exist, and they must be reconciled.
  4. Gradients are split into N chunks. In N−1 steps around the ring, each GPU accumulates the sum for one chunk. Each step sends 1/N of the gradients — so the communication is spread evenly rather than converging on one node.
  5. Another N−1 steps distribute each finished chunk back around the ring. Total traffic per GPU: 2·(N−1)/N × gradient bytes ≈ 2× the model size, independent of how many GPUs you have — which is why ring all-reduce scales.
  6. Every GPU applies the identical averaged gradient to its identical weights, so the replicas remain bit-identical. Any divergence here — different dropout seeds, non-deterministic reductions — silently breaks the guarantee.
  7. Gradients for the last layer are ready long before the first layer's. Frameworks bucket them and start all-reducing while the backward pass is still running, hiding most of the communication behind compute. Without this overlap, scaling efficiency collapses.
📐
The communication number worth memorising

Ring all-reduce moves 2×(N−1)/N × model_size bytes per GPU per step — about 2× the model size regardless of N. For a 7B model in bf16 that's ~28 GB per GPU per step. On 400 GB/s NVLink that's 70 ms; on a 25 GB/s network link it's over a second. This one calculation explains why intra-node bandwidth dictates your parallelism strategy.

Where the memory goes, and how ZeRO removes it

In plain data parallelism every GPU stores the full weights, the full gradients and the full optimizer state — but at any moment each GPU only needs a slice of the optimizer state to do its share of the update. ZeRO (and its PyTorch implementation, FSDP) shards what doesn't need duplicating.

ZeRO-3 trades bandwidth for memory

With parameters sharded, each layer's weights must be gathered just before use and released after. That's extra traffic on every forward and backward pass. It works beautifully inside a node on NVLink and degrades badly across a slow network — which is why the standard layout is FSDP within a node and other parallelism dimensions across nodes (Chapter 24).

Gradient accumulation and effective batch

If the per-device batch you need doesn't fit, split it into micro-batches and accumulate gradients before stepping:

effective_batch = per_device_batch × accumulation_steps × num_gpus

for i, micro in enumerate(micro_batches):
    loss = model(micro).loss / accumulation_steps   # ← divide, or your LR silently multiplies
    loss.backward()                                  # gradients accumulate
    if (i + 1) % accumulation_steps == 0:
        clip_grad_norm_(model.parameters(), 1.0)
        opt.step(); opt.zero_grad()
⚖️
Accumulation is free compute, not free bandwidth

Only the final micro-batch triggers the all-reduce, so accumulation also reduces communication per token — a useful trick when the network is the bottleneck. In DDP, remember to suppress synchronisation on intermediate micro-batches (no_sync()), or you all-reduce every one of them and lose the benefit entirely.

⚠️
Common mistakes
  • Not dividing the loss by accumulation steps. The effective learning rate multiplies, and the run diverges mysteriously.
  • Forgetting no_sync() during accumulation. You pay the full all-reduce on every micro-batch.
  • Different data order per rank without a shared seed policy. Either duplicated samples or silently skipped ones.
  • Rank-dependent control flow. If one rank skips a collective, everything hangs until the timeout — the worst failure to debug.
  • Scaling batch size without touching the schedule. Fewer steps at the same LR is a different, usually worse, run.
  • Benchmarking without warmup. The first steps include compilation, allocator growth and NCCL setup.

Interview drill

Warm-up: Why does ring all-reduce scale better than a parameter server?

How a strong answer sounds
A parameter server concentrates traffic: every worker sends gradients to the same place, so the server's bandwidth is a hard ceiling and it scales like O(N) on one link. Ring all-reduce distributes it — each GPU only ever talks to two neighbours, and the volume per GPU is about 2× the model size regardless of N, so adding GPUs doesn't increase per-link traffic. The cost is latency: 2(N−1) sequential steps, which is why very large clusters use hierarchical or tree-based algorithms that trade a little extra volume for fewer hops.

Deeper: A 70B model won't fit for training on 8×80 GB. Walk through your options in order.

How a strong answer sounds
First do the arithmetic: 70B in mixed precision with AdamW is roughly 70×16 = 1.1 TB for weights, gradients and optimizer state, against 640 GB of HBM — so plain DDP is impossible before activations. Options in order of cost: ZeRO-1 to shard optimizer state (removes the largest item); ZeRO-2 for gradients; ZeRO-3/FSDP to shard parameters too, which fits but adds all-gather traffic on every layer — acceptable within a node on NVLink. Add activation checkpointing to cut activation memory, and use bf16 with an 8-bit optimizer if still tight. If it still doesn't fit or the communication is too costly, move to tensor parallelism within the node plus pipeline parallelism across nodes (Chapter 24). I'd measure MFU at each step rather than assuming — the goal is throughput, not merely fitting.

🧠 Key takeaways

  • Data parallelism replicates the model and averages gradients with an all-reduce.
  • Ring all-reduce moves ~2× the model size per GPU per step, independent of GPU count.
  • ZeRO-1/2/3 shard optimizer state, gradients and parameters — the last trades bandwidth for memory.
  • Gradient accumulation enlarges the effective batch; divide the loss and suppress intermediate syncs.
  • Scaling efficiency dies from unoverlapped communication, stragglers and crossing node boundaries.

Check your understanding

How much data does each GPU send during one ring all-reduce of a 7B bf16 model?

2×(N−1)/N × 14 GB ≈ 28 GB. The constancy in N is exactly why ring all-reduce is the standard algorithm.

ZeRO-1 shards which component?

Optimizer state is usually the largest item (12 bytes/param for AdamW in mixed precision) and sharding it costs essentially no extra communication — the best ratio of the three stages.

Why is ZeRO-3 a poor fit across a slow network?

Sharded parameters have to be reassembled before use. On NVLink that's cheap; over a 25 GB/s link it dominates step time.

You use 4 accumulation steps but forget to divide the loss by 4. What happens?

Accumulated gradients are a sum, not a mean. The step is four times bigger than intended — a classic silent divergence.

Scaling efficiency is 92% within one node but 48% across four nodes. First thing to investigate?

The drop coincides exactly with leaving NVLink. Check achieved network bandwidth, collective algorithm, bucket sizes and overlap before touching anything about the model.

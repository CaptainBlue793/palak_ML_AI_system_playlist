Running Big Training Jobs

A month-long run on a thousand GPUs is an operations problem wearing a research hat. Hardware will fail, the loss will spike at 3am, and the difference between a successful run and a wasted million is checkpoint hygiene, monitoring and a rehearsed playbook.

  • Choose a checkpoint interval from failure rate and checkpoint cost
  • Recognise the standard failure modes and their signatures
  • Respond to a loss spike without destroying the run
  • Build the dashboard that tells you a run is healthy
  • Make a run resumable, elastic and reproducible enough

At scale, failure is the steady state

If one GPU fails on average every 50,000 hours, a 1,024-GPU job sees a failure roughly every two days — and that's before network flaps, storage hiccups, thermal events and the job that hangs because one rank took a different branch. The design goal is not to avoid failures; it is to make them cheap.

How often should you checkpoint?

Checkpoint too rarely and a failure costs hours of recomputation. Checkpoint too often and you spend the run writing to disk. There's an optimum, and it's worth computing rather than guessing.

Young's approximation: optimal interval ≈ √(2 × checkpoint_cost × MTBF). Asynchronous checkpointing — copy the state to host memory, then write to storage in the background — reduces the effective write cost to near zero and shifts the optimum much lower.

📦
What must be in a checkpoint

Model weights and optimizer state, the LR scheduler step, the RNG states for every rank, the data-loader position (which shard, which offset), the step count, and the config plus code commit. Miss the data position and “resume” silently re-trains on the same tokens. Miss the RNG state and your run is no longer reproducible from that point. Write to a temporary path and rename atomically, keep the last few plus periodic milestones, and verify a restore in the first hour — an untested checkpoint is a hope, not a backup.

The loss-spike playbook

Large runs spike. The wrong reaction — restarting from the same state with the same data — usually reproduces the spike and burns hours.

1 · Look at the gradient norm first

A spike in gradient norm almost always precedes the loss spike. If clipping is on and the norm still jumped an order of magnitude, the batch or the state is the problem, not the schedule.

2 · Identify the batch

Log the data shard and offsets per step. Replay the suspect batch alone against the pre-spike checkpoint: if it reproduces, you've found corrupted or pathological data (repeated tokens, a giant base64 blob, broken encoding).

3 · Roll back and skip

Restore the checkpoint from before the spike and skip or reshuffle the offending batches. This is the standard fix and it works far more often than anything cleverer.

4 · If it recurs, adjust the run

Lower the peak LR slightly, tighten gradient clipping, raise Adam's ε, or extend warmup. Frontier-run write-ups describe exactly these interventions — the process is empirical, not mystical.

5 · Record it

Write the intervention into the run log: step, symptom, action, outcome. Six weeks later nobody remembers why the LR changed at step 41,000, and the log is the only reason the result is reproducible.

Determinism: aim for “same conclusions”, not bit-identical

Bit-exact reproducibility at scale requires deterministic kernels, fixed collective algorithms, identical hardware and a fixed data order — and it costs throughput. What you actually need is: the same config and seed produce a run that reaches the same quality, and any checkpoint can be resumed to continue identically from that point. Log seeds, library versions, the container digest and the code commit with every checkpoint so a result can be re-created later.

Data at scale

📚

Pre-tokenize into shards

Tokenizing on the fly wastes CPU every epoch. Write packed, pre-tokenized shards of a few hundred MB, sequentially readable.

🔀

Shuffle at two levels

Shuffle shard order per epoch and maintain a shuffle buffer within a shard. Fully random access over a multi-terabyte corpus is not affordable.

↩️

Make the iterator resumable

Save (shard id, offset, epoch, seed) in the checkpoint. Otherwise a resume re-reads the same tokens — a quiet source of memorisation and wasted compute.

⚠️
Common mistakes
  • Never testing a restore. Restore from a checkpoint in the first hour of the run, not on the first failure at 3am.
  • Checkpointing the model but not the optimizer, scheduler, RNG or data position. The resume is a new, worse run.
  • Restarting a spiked run from the same state and data. It spikes again; roll back further and skip the batches.
  • No per-rank metrics. Averages hide the single straggler that is costing you 25% of the cluster.
  • Synchronous checkpointing at frontier scale. Use async or sharded distributed checkpointing; otherwise the whole cluster waits on storage.
  • No run log. Interventions unrecorded means results unreproducible and lessons unlearned.
🎤
Interview drill

Warm-up: Failures every 12 hours, checkpoints take 6 minutes. How often do you checkpoint, and why?

How a strong answer sounds
Young's approximation gives √(2 × 0.1 h × 12 h) ≈ 1.5 hours, so roughly every 90 minutes — at that point the expected write overhead and the expected recomputation loss are balanced, and the total waste is a couple of percent. But I'd first try to make the write cheap: asynchronous, sharded checkpointing that copies state to host memory and writes in the background reduces the effective cost to near zero, which moves the optimum down to every 15–30 minutes and cuts the worst-case loss dramatically. I'd also verify a restore immediately and alert on rising write times, since storage saturation is what silently breaks this calculation.

Deeper: Day 9 of a 14-day run, loss jumps from 2.1 to 6.8. Walk me through the next hour.

How a strong answer sounds
First, stop the bleeding: pause or let it run only if the loss is recovering — a single-step spike that recovers may be survivable, a diverging one is not. Then evidence: look at the gradient-norm trace just before the spike, per-rank losses (one rank diverging suggests hardware or corrupted shards rather than a data batch), and the logged shard/offset for the affected steps. Replay the suspect batches against the last good checkpoint in a small side job. If it reproduces, roll back to before the spike, skip or reshuffle those batches, and resume. If it doesn't reproduce, suspect hardware — check ECC counters and Xid logs on the ranks involved, and restart on different nodes. If it recurs after a clean rollback, adjust the run: lower peak LR modestly, tighten clipping, raise Adam epsilon. Throughout, record the timeline in the run log, and don't make two changes at once — you'll never know which one worked.

🧠 Key takeaways

  • At thousands of GPUs, failures are routine — engineer for cheap recovery, not for avoidance.
  • Optimal checkpoint interval ≈ √(2 × checkpoint cost × MTBF); async checkpointing moves it much lower.
  • A checkpoint must include optimizer, scheduler, RNG and data-loader position, and a restore must be tested.
  • Handle loss spikes by rolling back and skipping batches before changing hyperparameters.
  • Monitor per-rank step time, gradient norm, MFU and checkpoint write time — and keep a run log.

Check your understanding

Your resume works but the model re-learns tokens it already saw. What was missing from the checkpoint?

Without the iterator position, the resume starts the data stream from the beginning. Training continues and looks fine while silently repeating data.

All ranks are alive, GPU utilization is 100%, and no step has completed for 20 minutes. Most likely cause?

Classic NCCL deadlock, usually from rank-dependent control flow (an early return, a conditional eval, a rank-specific exception). Set collective timeouts and dump per-rank stacks.

MTBF is 24 hours and a checkpoint takes 6 minutes. Roughly what's the optimal interval?

√(2 × 0.1 h × 24 h) ≈ 2.2 hours. Making the checkpoint asynchronous is usually a better move than tuning this number.

The loss spikes at step 60k. What do you do first?

Diagnose before intervening. Gradient norm usually spikes first, and the logged shard/offset tells you whether a specific batch is responsible — in which case rolling back and skipping it is the cheapest correct fix.

Step time increased 30% overnight with no code change. What do you check first?

Synchronous training runs at the speed of its slowest rank. A thermally throttled GPU or a degraded NIC on one node taxes the entire cluster — which is why per-rank timing belongs on the dashboard.

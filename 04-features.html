Features & Representations

A model only ever sees numbers. Everything between your raw data and those numbers — scaling, encoding, aggregating, embedding — is representation, and it decides how hard the learning problem is. Deep learning automated a lot of this. It did not automate all of it.

  • Transform numeric features so optimizers can actually work
  • Encode categoricals — one-hot, hashing, target encoding, embeddings
  • Build time, sequence and interaction features without leaking
  • Know when a learned representation replaces hand-engineering, and when it can't
  • Weigh a feature's value against its serving latency and maintenance cost

What counts as a feature

A feature is any number derived from data that is available at prediction time, computable inside the latency budget, and computed identically in training and serving. Fail any of those three and it is not a feature, it is a future bug.

⏱️

Available in time

Known before the event you're predicting. Pin every feature to the prediction timestamp (Chapter 29 makes this a system property).

⚡

Affordable

A feature requiring a 300 ms join is unusable in a 50 ms budget. Precompute it, cache it, or drop it.

🔁

Reproducible

The same definition offline and online. Two implementations of “average order value” is the classic skew bug.

Numeric features: shape matters more than you think

Raw numbers are rarely model-ready. Incomes span four orders of magnitude, ages span two, and gradient-based optimizers hate that: the loss surface becomes a long thin valley and training crawls. Play with the transforms below.

Which transform when
  • Linear models and neural nets: standardize (mean 0, std 1). Non-negotiable — it changes convergence by an order of magnitude.
  • Heavy-tailed positives (income, counts, durations, prices): log1p first, then standardize.
  • Trees and gradient boosting: scaling is irrelevant — they only compare thresholds. Don't waste effort.
  • Bounded inputs for images/audio: min-max to [0,1] or [-1,1] to match what the pretrained network saw.

Missing values are information

Never silently impute and move on. NULL usually means something: the field didn't exist yet, the user skipped it, the upstream service timed out. Impute and add a boolean was_missing flag so the model can use the fact of absence — and so a spike in missingness shows up in monitoring instead of quietly shifting your median.

Two different categories sharing a slot is survivable: the model just sees a slightly blurred signal, and rare values collide with other rare values. This is how ad-click systems handle billions of feature values in fixed memory (Chapter 43).

🎯
Target encoding: powerful and dangerous

Replacing “seller_id” with “that seller's historical fraud rate” is often the strongest feature you can build — and the easiest way to leak. The mean must be computed out-of-fold (or from strictly earlier time) and smoothed toward the global mean for rare values: (sum + m·prior) / (count + m). Without both, the model memorises the target and your validation score is fiction.

Interactions and crosses

Linear models can't learn “this feature matters only when that other one is true”. You give it to them explicitly as a cross: country × device, hour × is_weekend, query_token × product_category. Crossed features were the backbone of pre-deep-learning ad systems and are still standard in the “wide” half of wide-and-deep models.

🌳 Trees get them free

A decision tree splitting on country then device is an interaction. That's a big part of why GBDTs dominate tabular problems with minimal feature work.

🧠 Deep nets learn them

Hidden layers compose inputs multiplicatively-ish; attention learns which features interact per example. But with limited data, an explicit cross still beats hoping.

Time and sequence features

Timestamps are the richest and most leak-prone column you have. Three things to do with them:

🔁 Cyclical encoding

Hour 23 and hour 0 are adjacent, but as a number they're 23 apart. Encode as sin(2πh/24), cos(2πh/24) so the distance is right.

📊 Rolling aggregates

Count / mean / max over the last 1h, 24h, 30d, strictly before the prediction time. The workhorse of fraud and recommendation features.

⏳ Recency & gaps

“Seconds since previous event”, “days since first seen”. Cheap, strong, and meaningful for nearly every user-level model.

Text, images and the rise of learned representations

For unstructured data, hand-engineering lost. The progression is worth knowing because each step still appears in production systems.

Bag of words / n-grams

Count each word. Sparse, enormous, no notion of meaning — “great” and “fantastic” are unrelated columns. Still a fine baseline and very fast.

TF-IDF

Weight words by rarity so “the” stops dominating. Powers BM25 and classic search; still the lexical half of hybrid retrieval (Chapter 21).

Word embeddings

word2vec/GloVe: one dense vector per word, learned from context. Meaning becomes geometry — but one vector per word, regardless of sentence.

Contextual embeddings

BERT-style encoders give each token a vector that depends on its sentence, so “bank” differs by context. This is what modern embedding models serve (Chapter 15).

End-to-end learned

The network consumes raw tokens or pixels and learns every intermediate representation itself. Your job shifts from crafting features to curating data and designing the input pipeline.

🧩
“Deep learning means no feature engineering” is half true

It's true within a modality: you don't design edge detectors any more. It's false for the system. Someone still decides which 30-day aggregates get fetched, which user history is concatenated, what goes into the prompt, and how a categorical id maps to an embedding row. In recommender and tabular systems, feature work remains most of the measurable gains.

⚠️
Common mistakes
  • Fitting encoders on the full dataset. Scalers, target encoders and vocabularies must be fitted on training data only — otherwise validation is contaminated.
  • No plan for unseen categories. Production will send you a country code, app version or merchant you've never seen. Reserve an explicit <UNK> slot and test it.
  • Rolling windows that include the present. “Purchases in the last 7 days” computed with <= instead of < includes the event you're predicting.
  • Two implementations of one feature. A SQL version for training and a Python version for serving will diverge. One definition, one code path (Chapter 29).
  • Hoarding features. 400 features with 30 doing the work is 370 pipelines to maintain and 370 chances of a silent null. Prune by importance and by cost.
🎤
Interview drill

Warm-up: Design the feature set for “will this food delivery be late?”, predicted at order time.

How a strong answer sounds
Three groups. Order: item count, prep-time estimate, price, is-scheduled. Context: hour and day cyclically encoded, weather, distance, current rain flag. Aggregates as of now: restaurant's median prep time over the last 30 days and last 2 hours, couriers available within 3 km, restaurant's current open-order backlog, courier's recent on-time rate. Everything must be computed with a strict “before order time” cut-off and served from an online store within a few milliseconds, with the same definitions used to build the training set — so I'd define them once in a feature repository rather than in two places.

Deeper: You have 2 million distinct seller IDs and need them in a neural ranker. Options?

How a strong answer sounds
An embedding table of 2M rows is memory-heavy and most rows will be undertrained, so: keep explicit embeddings for the head sellers that have enough traffic, hash the long tail into a shared bucket space, and add descriptive features (tenure, category, rating, historical rates computed out-of-fold) so a cold seller still gets a reasonable score from its attributes. That combination gives capacity where data exists, graceful degradation where it doesn't, and a fixed memory footprint — which is also what makes the model servable.

🧠 Key takeaways

  • A feature must be available in time, affordable at serving, and defined identically offline and online.
  • Standardize (and log-transform skewed positives) for gradient-based models; skip it for trees.
  • Pick a categorical encoding by cardinality and model type; target encoding needs out-of-fold computation.
  • Encode cyclical time on a circle and build rolling aggregates with a strict time cut-off.
  • Judge features by lift per millisecond and per pipeline, not lift alone.

Check your understanding

You're training gradient-boosted trees on tabular data. Which preprocessing step is least useful?

Trees split on thresholds, so monotone rescaling changes nothing. The other three all add real information.

Encoding hour-of-day as the integers 0–23 in a neural net causes what problem?

The model has to waste capacity learning that the ends wrap around. Sin/cos encoding puts them next to each other by construction.

Target encoding a merchant_id column with the overall fraud rate per merchant, computed on the whole training set, causes…

For rare merchants the encoded value is essentially the row's own label. Compute it out-of-fold (or from strictly earlier data) and smooth toward the prior.

What is the main advantage of the hashing trick over one-hot encoding?

Hashing bounds the feature space in advance, so a streaming system with an unbounded vocabulary still fits in a known amount of memory. The cost is collisions and lost interpretability.

A feature adds +0.002 AUC but requires a 250 ms third-party API call per prediction, in a service with a 100 ms p99 budget. What do you do?

A feature you cannot compute in time is not a feature. If the signal is genuinely valuable, move it offline: refresh it in the background and read a cached value at request time — accepting slight staleness in exchange for meeting the budget.
